# 工程案例：应用升级与知识库更新如何保护用户资料

## 学习目标与案例范围

用知栈 1.2.0 的实现理解三个独立对象：APK 是程序，内置课程是随程序附带的内容快照，个人笔记和项目是本机数据库。它们有不同版本和更新规则，不能用一个“更新成功”概括。先明确输入格式、大小上限和错误处理，再把本案例当作状态机与边界校验练习。

本案例描述本版实现和自动测试范围。Android 下载、系统授权与覆盖安装仍需手机验收；没有发布地址时不发生真实在线版本检测。

## 一条完整的软件更新链路

配置 HTTPS 版本清单地址后，应用打开或回到前台时最多每天尝试一次；用户可随时手动检查。清单包含应用 ID、versionCode、版本名、最低系统版本、更新说明、APK URL、字节数和 SHA-256。先验证字段，再比较版本；网络失败显示失败，不能当作“已经最新”。

下载到私有临时文件后，核对大小和摘要，再读取 APK 实际包名、版本、最低系统和签名。清单必须与 APK 内容一致，而且签名要与当前安装版本相同。本版采用精确签名集合比较，不支持签名轮换。通过后等待用户点击安装，Android 系统处理授权与安装确认；打开安装器只是交接，不是成功证明。

为什么使用 versionCode 比较？它是发布者递增的整数；展示字符串的字典序会把 1.10.0 与 1.9.0 排错。[Android 版本管理说明](https://developer.android.com/studio/publish/versioning) 区分了展示版本与内部版本码。发布者不能只修改清单版本而复用旧 APK；客户端会核对真实安装包。

## 摘要与签名各自解决什么

SHA-256 用来核对收到的字节是否匹配清单。如果攻击者同时替换清单和 APK，仅靠摘要不能证明发布者身份。HTTPS 保护连接的服务端身份与传输；与已安装应用相同的 APK 签名才用于确认升级包延续原安装身份。系统安装器仍有自己的校验。

本版下载有大小上限、超时、取消和磁盘空间检查；失败删除部分文件，已有资料不参与下载事务。取消操作用任务 ID 关联，迟到的下载成功事件不能把界面重新变成“可安装”。应用进程结束后重新下载，本版没有断点续传。

## 内容更新为什么不能直接覆盖

用户可能改过课程正文。只比较文章 ID 并替换，会丢掉用户劳动；全部追加又会反复制造副本。知栈记录内置原文摘要与内容版本：未改动正文可更新，同时保留笔记、进度和收藏；已改动正文保留原文并生成“内置新版”；回收站文章不复活；重复更新没有新变化。

当一篇目录链接到被保留旧稿的文章时，新版目录应指向对应的新版副本。只复制正文而不处理关联引用，会让用户从新目录回到旧内容。数据库更新在事务中完成，不能在半套课程写入后就记录成功。

APK 覆盖安装保持原包名、签名、WebView origin 和数据库名。知栈本版不删库重建；但实际升级是否保留全部数据仍需在目标手机测试。卸载或清除数据与覆盖安装不同，会失去本机资料。

## 练习与验收表

先备份实验资料，写下三条不同的个人笔记，再执行以下演练。没有 HTTPS 地址或手机时，只把前端模拟与本机内容更新标为已测。

| 输入 / 操作 | 预期 |
| --- | --- |
| 同一或更低 versionCode | 不提供降级安装 |
| HTTP 地址、其他包名清单 | 拒绝并解释原因 |
| 下载截断或 SHA 不符 | 不允许安装，支持重新下载 |
| 取消后仍收到旧进度 | 保持取消状态 |
| 更换清单地址 | 清理旧候选版本，避免装错来源 |
| 修改课程正文后更新资料 | 修改保留，新内容为副本 |
| 未改正文但有个人笔记 | 新正文与原笔记同时保留 |
| 再次更新相同资料 | 不继续制造副本 |

通过条件：结果与表格一致，并把网络模拟、JVM 校验测试、浏览器测试和手机安装验收分列记录。只有最后一项能证明系统安装流程在那台设备上实际完成。

## 自测与参考答案

“下载进度 100%”等于可安装吗？不等于，还要做摘要和安装信息校验。

“打开系统安装界面”能显示“升级成功”吗？不能，用户可能取消、系统可能拒绝；重新打开后的真实版本才是必要证据之一。

“自动检查失败”应删除现有笔记吗？不能，两者没有依赖关系。这个边界让一个网络功能失效时，离线核心功能仍能工作。

回到 [复现方法](doc:lessons-05)，设计一条能使“取消后仍可安装”缺陷出现的最小事件顺序。这种乱序测试比单纯连续点击十次更能检验状态管理。
