# 问题复现：把一句“不能用”变成可以修复的证据

## 目标与常见误区

目标是让没有参与现场的人，在相同条件下观察到同一问题，并能区分多个可能原因。适用于手机安装、网络断开、SD 补传、线程退出和 UI 异常。先读 [从日志到根因](doc:lessons-02)。本章用假设场景演示推理，不把示例当作已经发生的故障结论。

症状、触发、根因、修复是四件事。“安装失败”是症状；“覆盖安装时报签名不一致”是更多证据；还需确认两个 APK 的签名和包名，才能判断是否确由签名变更导致。仅知道手机型号是 S24，不能断言是系统拦截、CPU 架构或 APK 损坏。

## 可直接复制的实验记录模板

```text
标题：具体动作 + 实际异常
目标：应该出现的可观察结果
环境：硬件/系统、应用版本与版本码、构建或文件 SHA-256
前置：已有数据、网络、电源、权限、是否升级安装
步骤：1. ... 2. ... 3. ...（每步只有一个动作）
预期：界面、退出码、文件大小或日志中的明确标志
实际：完整错误文本、首次异常前后的时间线
频率：失败次数 / 总尝试次数，是否可稳定复现
影响：功能不可用、数据丢失、还是仅展示不一致
已排除：采用何种测试排除，不只写“应该没问题”
假设：原因 A / B，以及各自预测的不同结果
下一试验：只改变哪个变量，观察哪个指标
修复后：同一复现步骤结果 + 相邻功能回归结果
未验证：设备、边界或故障注入仍未覆盖的部分
```

日志只保留与复现相关的范围，保留原始时间戳和版本信息；分享前检查令牌、密钥、个人路径和对话内容。摘要用于阅读，原始材料用于复核，两者不能互相代替。

## 实验一：手机无法安装

先收集安装器的完整错误文字、系统版本、APK 文件大小与 SHA-256、已有安装版本。保留原应用与资料，不把卸载当作第一步。对比发行包和手机收到的文件，若不一致先解决传输；一致再查包名、签名、版本码、最低系统及系统提示。

如果系统提示不允许此来源安装，应按该提示理解授权状态；没有这个证据时不要要求用户关闭安全功能。能连接开发工具时可记录安装返回的明确状态码；没有连接时如实写“缺少系统返回码”。观察不足时结论应是“待定位”，不是替用户猜一个确定原因。

完成条件：其他人拿到记录后，知道需要哪个 APK、哪种已有安装状态、在哪一步出现什么错误。此模板也解释了为什么桌面浏览器测试通过，不能解决真实手机安装结论。

## 实验二：补传速度变化

把总时间拆成排队等待、SD 读取、组帧、网络发送、ACK 与重试；区分有效字节与重传字节。使用 `有效字节 / 总耗时 / 1024` 得到 KiB/s，写清时间窗口是否包含断线等待。不要混用 kB/s、KiB/s 与音频实时倍率。

假设 A：SD 读慢；预测读取耗时占比增加。假设 B：ACK 等待慢；预测数据已发送但确认间隔增长。先增加分段计时再选择优化，否则一次改任务优先级、窗口和频率，即使变快也不知道是谁起作用。

练习：10 MiB 有效数据用时 40 s，其中 10 s 等重连。全程速度是 256 KiB/s；排除等待的活跃阶段约 341.3 KiB/s。两个数字描述不同体验，应同时保留口径，不能只报告较大的一个。

## 验收、反证与回归

修复前保存失败证据；修复后重跑相同步骤，确认预期行为恢复。再测相邻边界，例如取消下载修复后还要测重新下载、切换页面、修改地址和迟到回调。有限回归通过支持当前结论，但不能证明从此不会出现任何问题。

能推翻假设的试验比重复观察更有用：若怀疑队列关闭丢数据，就固定输入数量并核对输出守恒；若怀疑版本判断错误，就保持 APK 不变、只改变显示版本名，检查版本码比较是否仍正确。

## 自测与参考答案

一份截取日志没有崩溃堆栈，可以直接定为内存不足吗？不能。记录最后可见行为和证据缺口，补重启原因、异常信息与内存指标后再区分原因。

修改后一次通过，为什么还要测十次？重复测试能发现概率性问题，但次数应服务于明确假设；同样环境盲目重复不能覆盖断网、取消和进程重启。

记录中最重要的是“解决办法”吗？还包括证明办法有效的条件与反例。后续工程条件改变时，这些信息能帮助判断旧经验是否仍适用。
