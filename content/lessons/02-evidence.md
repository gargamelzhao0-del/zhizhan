# 02 · 排障证据：把重启现象变成可验证的根因

## 案例范围与目标

来源：[诊断与崩溃定位](doc:handbook-20)、[测试方法](doc:handbook-21)、[历史问题](doc:handbook-22)。本课总结方法，不宣称已复现或修复历史上的全部重启。预计 60 分钟，完成一份别人能复核的排障记录。

## 三种句子不能混写

事实：“重启前最后一条保存日志来自补传任务。”推断：“补传与重启可能相关。”根因结论：“某处非法写入导致特定异常，修复后用原复现条件验证。”最后一句需要比前两句更多证据。

最后打印日志的任务不一定是破坏内存的任务。堆破坏可能早发生、晚暴露；串口截取可能缺少崩溃头。地址必须用同一次构建的 ELF 解析，不能拿新固件符号解释旧地址。对应不上版本时，先保留未知。

## 最小证据包

| 项目 | 为什么需要 |
| --- | --- |
| 固件版本、SHA、ELF、配置 | 确定代码和地址属于哪次构建 |
| 启动原因、完整异常头、回溯 | 区分 watchdog、异常、掉电等候选 |
| 时间线与操作步骤 | 找到稳定触发条件 |
| 内存、栈、队列与资源占用 | 判断压力与生命周期风险 |
| 对照版本和变更点 | 控制因果推断范围 |

没有保存完整崩溃证据时，结论应写“目前无法唯一定位”，而不是用常见原因填空。

## 一次可复用的调查流程

先固定输入和环境，再做一次只改一个主要变量的对照。举例：保持同一音频文件、网络条件、任务配置，只改变预读缓冲策略。若失败频率下降，还需确认负载是否也下降，不能马上归因为“预读修好了内存”。

对已经明确的缺陷，应能说明触发条件、违反的约束、修复如何恢复约束，以及对应的回归方法。例如缓冲的所有者释放后，另一个任务仍读该地址；修复重点是交接和生命周期，不是把延时再加 100 ms。

## 动手练习

给以下材料写结论：一次重启，前一秒记录空闲堆 20 KiB，缺少异常头，重启后正常运行。正确结论只能是“观察到重启与该堆快照”，不能直接断言内存泄漏、栈溢出或电压跌落。下一步应获取重启原因、完整日志、匹配 ELF，并明确复现步骤。

再写一个回归表：原触发场景、压力场景、取消/重连、低资源、持续运行。记录运行时长、次数、失败次数和漏测项。十次没有失败可以报告 0/10，不能报告“再也不会重启”。

## 自测与答案

**加大栈后没重启就是栈溢出吗？** 不是，内存布局和调度变化也可能掩盖问题，需要对应证据。

**日志越多越好吗？** 不一定，打印可能改变时序与负载。优先记录状态转换、关键计数和错误上下文。

**验收：** 你的记录必须分别列出已证实、待验证、已排除及依据，别人能照着复现，而不是只看见一个“已解决”。
