Module 01 · 规范与门禁

项目结构、风格与规范.

工程化第一步是让代码“可被他人维护”：统一的目录、命名、接口与错误码规范，加上能自动检查的门禁。规范不靠自觉，靠自动化。

前置：C 语言与一次完整的工程构建/评审经历。◷ 约 42 分钟◈ 三平台工程实践对照⚑ 主机模型；目标构建与测量按章验收能力目标：能为一套嵌入式代码定出可自动检查的目录/命名/接口/提交规范。
本章速览
  • 规范要能自动检查，评审只关注设计与逻辑。
  • 统一目录/命名/接口/错误码，降低维护成本。
  • 提交信息要能追溯变更。

1.1 让代码可维护的四类规范

工程化的第一步不是写业务，而是定“别人能接手”的规范：目录/模块、命名/风格、接口/错误码、文档/提交。把可机械检查的规则放进门禁，评审只关注设计与逻辑。

1.2 真实证据：门禁判定

门禁把检查分为“硬性失败”与“警告”：硬性失败必须归零，警告只计数。下面这段程序跑出真实判定：

/* host_gate.c —— 自动化门禁：静态检查 + 测试结果的合并判定（主机可运行）。 * CI 门禁把多项检查聚合：任一硬性检查失败则整体失败；警告不阻塞但计数。 * 编译运行：gcc -std=c11 -Wall -Wextra -O2 host_gate.c -o host_gate && ./host_gate */#include <stdio.h>#include <string.h>typedef struct { const char *name; int hard; int ok; } check_t;int main(void) {    int ok = 1;    check_t checks[] = {        {"编译通过", 1, 1}, {"单元测试", 1, 1}, {"行宽<=100", 0, 0},        {"无 TODO", 1, 1}, {"覆盖率>=80", 0, 1},    };    int n = (int)(sizeof(checks) / sizeof(checks[0])), hard_fail = 0, warn = 0;    for (int i = 0; i < n; i++) {        printf("  %-12s hard=%d ok=%d\n", checks[i].name, checks[i].hard, checks[i].ok);        if (!checks[i].ok) { if (checks[i].hard) hard_fail++; else warn++; }    }    printf("硬性失败=%d 警告=%d → 门禁 %s\n", hard_fail, warn, hard_fail ? "FAIL" : "PASS");    if (!(hard_fail == 0 && warn == 1)) ok = 0;    printf("\n%s\n", ok ? "RESULT: PASS" : "RESULT: FAIL");    return ok ? 0 : 1;}

1.5 常见误区与排障

失败路径与排障
  • 规范只写在文档：无人执行。
  • 命名/目录随意：新人无法定位。
  • 错误码不统一：上层无法判断。
  • 提交信息无意义：无法回溯。
◆ 自测 · Module 01（先答再看）

  1. 为什么规范要“可自动检查”？

    查看答案

    人工评审不稳定且有成本；可机械判定的规则交给工具，评审聚焦设计。规范只有可执行才可持续。

  2. 门禁里“硬性失败”和“警告”有什么区别？

    查看答案

    硬性失败必须为 0，否则构建/合并失败；警告只计数、不阻塞（可先软后硬）。这类分级让门禁既严格又能渐进落地。

  3. 评审清单为什么只保留“工具查不了”的项？

    查看答案

    把形式项交给工具后，人能专注真正的设计与逻辑问题，避免把时间花在机器能判的地方。

  6. ⑥ 追溯（M07/M10）——需求↔测试矩阵；验收：未覆盖项显式列出。
  7. ⑦ 诊断（M08）——保留现场 + 二分；验收：可定位到版本/参数。
  8. ⑧ 选型（M09）——总成本 + 替代料；验收：BOM 可算、有备选。
  9. ⑨ 回归（M11）——故障注入 + 长跑 + 基线；验收：恢复率与阈值可测。
