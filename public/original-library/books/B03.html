Module 01 · 所有权与借用

所有权与借用：对着 C 讲

第①册反复强调"指针的三种错"：悬垂、别名、忘记释放。C 靠纪律避免它们，Rust 靠编译器。 这一节不从语法讲起，而是先看你已经熟悉的 C 会在哪里出错，再看 move 与借用规则如何把这三类错误变成编译错误 —— 以及它在运行期到底花不花钱。

◷ 约 70 分钟◈ 真实 rustc 报错与反汇编⚑ 全册的地基

1.1 先看 C 的三张"债"

下面三段 C 代码都能编过（最多一条警告），但都埋着雷。Rust 存在的第一理由，就是让这三件事在编译期不可能发生：

debt_c.c — 悬垂 / 忘释放 / 越界别名（编译期不报） C 
/* debt_c.c —— 三类由"纪律"兜底的 bug */
#include <stdint.h>

/* ① 悬垂：返回指向栈上数组的指针（GCC 只给一条警告） */
char* dangling(void) { char buf[8]; buf[0] = 'h'; return buf; }

/* ② 忘释放：并非所有 return 路径都记得释放 */
int use_resource(int *handle, int fail_early) {
    *handle = 1;                   /* 获取资源 */
    if (fail_early) return -1;     /* ✕ 忘了释放 */
    *handle = 0;                   /* 释放 */
    return 0;
}

/* ③ 越界别名：p 与调用方共享，且 i==n 时越界写 */
void alias(uint8_t *p, uint32_t n) {
    for (uint32_t i = 0; i <= n; i++) p[i] = (uint8_t)(p[i] + 1);
}
债C 里为什么防不住Rust 用什么拦
悬垂函数返回 char*，没人知道它指向栈；调用方照用生命周期：借用不能比它引用的数据活得久
忘释放释放是"约定"，任何一条 return 都可能漏所有权：值离开作用域自动 Drop
别名多个指针可同时指向同一块，读写不受限借用规则：要么多个 &、要么一个 &mut

1.2 所有权：move 把"谁负责"写进类型

在 Rust 里，每个值有且只有一个所有者；把值交给别人叫 move，之后原来的名字不能再用。 这不是"拷贝"，也不是"置空"——是编译器在类型层面把所有权转移记下来了。

ownership.rs — move 之后原绑定失效（编译期） Rust 
// ownership.rs —— move 把所有权在类型层面移走
#![no_std]

pub struct Buf { data: [u8; 8] }

pub fn consume(b: Buf) -> u8 { b.data[0] }

pub fn demo() -> u8 {
    let b = Buf { data: [0; 8] };
    let s = consume(b);      // 所有权移入 consume
    // let t = b.data[0];    // ✕ 编译错误：use of moved value: `b`
    s
}

对照上一节的 C：consume(b) 在 C 里按值传参只是拷贝，原 b 照样能用， 编译器不会、也无法阻止你之后继续用 b。Rust 把"这个值已经交出去了"记成了类型事实 —— 忘记释放因此从"约定"变成"不可能"：值没人用时会自动析构。

FIG 1.1 同一块缓冲：C 的"拷贝指针" vs Rust 的"移动所有权"
左边是 C 里"把指针传过去"的常态：两个名字、一块内存，谁改都行。右边 Rust 的 move 只转移、不复制—— 同一时刻只有一个有效所有者，于是"重复释放 / 释放后使用"从源头消失。

1.3 借用：& 与 &mut 的别名规则

你不想转移所有权（比如只想读一下），就借用：&x 是共享借用（只读，可多个）， &mut x 是独占借用（可写，同时只能一个）。"共享 XOR 独占"这一条，恰好把 C 里"读写同一块、结果不可预期"的问题变成编译错误。

borrow.rs — 共享与独占借用，顺序正确即可编译 Rust 
// borrow.rs —— 同一时刻"多个只读"或"一个可写"，二选一
#![no_std]

pub fn sum(xs: &[u8]) -> u32 {
    let mut s = 0u32; let mut i = 0usize;
    while i < xs.len() { s = s.wrapping_add(xs[i] as u32); i += 1; }
    s
}
pub fn inc(xs: &mut [u8]) {
    let mut i = 0usize;
    while i < xs.len() { xs[i] = xs[i].wrapping_add(1); i += 1; }
}
pub fn demo() -> u32 {
    let mut a = [1u8, 2, 3];
    inc(&mut a);       // 独占借用：这一步可写
    sum(&a)            // 独占借用结束后，才共享借用
}
◆ 这条规则到底拦住了什么

C 里最常见的"迭代器失效 / 边遍历边改 / 两个模块同时读写一个缓冲"——本质都是别名问题。 Rust 的"共享 XOR 独占"让"正在被别人读的时候去写它"根本编译不过。 这也是为什么 Rust 能宣称"无数据竞争"：数据竞争的前提就是"又有共享访问、又有写"。

1.5 生命周期：借用不能超过它引用的数据

生命周期标注（'a）不是为了"让编译器开心"，而是把你本来就该有的约束写显式： 一个持有借用的结构体，必须保证它引用的数据活得比它久。下面是最常见的形态——一个解析器借用一段字节：

lifetime_ok.rs — 结构体持有借用，生命周期显式绑定 Rust 
// lifetime_ok.rs —— 'a 把"解析器不能比数据活得久"写进类型
#![no_std]

pub struct Parser<'a> { data: &'a [u8] }

impl<'a> Parser<'a> {
    pub fn new(data: &'a [u8]) -> Self { Self { data } }
    pub fn first(&self) -> Option<u8> { self.data.first().copied() }
}

pub fn demo() -> Option<u8> {
    let bytes = [1u8, 2, 3];
    let p = Parser::new(&bytes);   // p 借用 bytes
    p.first()                      // bytes 仍活着，合法
}

把 bytes 与 p 的声明顺序调换（先建 p 再建 bytes），编译器会报 borrowed value does not live long enough。这在 C 里就是"结构体里存了个已经失效的指针"——而 C 不会告诉你。

1.6 代价：借用与所有权在运行期花不花钱

Module 02 · 类型即约束

用类型系统编码硬件约束

C 里"这个参数是寄存器地址、不是随便一个整数"只能写在注释里；Rust 用 newtype 把它写进类型。 更进一步：用类型状态机让"没初始化就用"变成编译错误 —— 这一节把"硬件使用顺序"变成类型系统能检查的东西。

◷ 约 65 分钟◈ newtype · 类型状态机⚑ 0 运行时开销

2.1 newtype：把"同一底层类型的不同含义"分开

嵌入式里到处都是 u32：寄存器地址、引脚号、超时毫秒数、位掩码……它们底层一样， 所以 C 里可以随便互传。Rust 用一个只包一层的 newtype（struct RegAddr(u32)）把它们分成不同类型，且零运行时开销。

newtype.rs — 寄存器地址与普通整数分开 Rust 
// newtype.rs —— 同一底层类型，不同"类型身份"
#![no_std]

#[derive(Clone, Copy)]
pub struct RegAddr(pub u32);
#[derive(Clone, Copy)]
pub struct PinId(pub u8);

pub fn write_reg(a: RegAddr, v: u32) {
    unsafe { core::ptr::write_volatile(a.0 as *mut u32, v) }
}

pub fn demo() {
    let a = RegAddr(0x4001_0000);
    write_reg(a, 1);
    // write_reg(0x4001_0000, 1);   // ✕ u32 不能隐式变成 RegAddr
}

RegAddr 与 u32 在机器码里完全一样（就是个 u32）， 但编译器不再允许你把一个"地址"误传给收"毫秒"的函数。这正是第①册"类型即护栏"在 Rust 里的自然延伸。

2.2 类型状态机：让"没初始化就用"编译不过

硬件最危险的错误之一是"外设没配置就去读写"。C 靠"记得先调 init()"；Rust 可以把状态编码进类型： 用两个零大小标记类型 Uninit/Ready，把 write() 只实现在 Ready 上。

typestate.rs — init() 之后类型才变成 Ready Rust 
// typestate.rs —— 类型状态机：只有 Ready 才能 write
#![no_std]
use core::marker::PhantomData;

pub struct Uninit;
pub struct Ready;

pub struct Uart<State> {
    base: u32,
    _s: PhantomData<State>,
}
impl Uart<Uninit> {
    pub fn new(base: u32) -> Self { Self { base, _s: PhantomData } }
    pub fn init(self) -> Uart<Ready> {
        // 实际这里配置寄存器；返回一个新的类型
        Uart { base: self.base, _s: PhantomData }
    }
}
impl Uart<Ready> {
    pub fn write(&mut self, b: u8) {
        unsafe { core::ptr::write_volatile((self.base + 4) as *mut u32, b as u32) }
    }
}

pub fn demo() {
    let mut u = Uart::new(0x4001_3800).init();  // 先 init，类型变为 Uart<Ready>
    u.write(0x41);                              // 再 write
}

PhantomData<State> 是零大小的（运行期不占字节），它只是让编译器把状态记在类型里。 关键在于：write 根本不存在于 Uart<Uninit> 上 —— 提前调用不是"运行时出错"，而是没有这个方法。

FIG 2.1 类型状态机：状态在类型里，不在变量里
状态迁移不是"运行时改一个 enum 字段"，而是类型在变：init() 消费 Uart<Uninit>、返回 Uart<Ready>。所以"没 init 就 write"根本没有对应方法可调。
typestate_fail.rs — 反面：没 init 就 write Rust 
// 反面：未初始化的 Uart 没有 write()
#![no_std]

pub struct Uninit; pub struct Ready;

impl Uart<Uninit> { pub fn new(base: u32) -> Self { Self { base, _s: PhantomData } } }

2.5 什么时候别用类型体操

newtype 和类型状态机很优雅，但不是越多越好：状态一多、跳转复杂时，硬套类型状态机会让代码难读，此时用数据枚举（enum）表达状态更合适。用类型消灭"真实发生过"的错误，而不是为每个 bit 都建一个类型。

◆ 本章要点
  • newtype struct X(u32)：把同一底层类型的不同含义分开，零运行时开销。
  • 类型状态机：用 Uninit/Ready 标记类型，让"没 init 就用"变成"没有这个方法"。
  • PhantomData<State> 是零大小的，状态只存在于类型层面。
  • 编译器会指出方法"在哪个类型上存在"，比 C 的"行为诡异"好得多。
  • 护栏要加在值得的地方：跨模块接口、易混单位/地址、状态码。

Module 03 · no_std 与 panic

no_std 与 panic

MCU 上没有操作系统、没有文件、没有 Vec。Rust 用 no_std 把语言核心（core）留下、把依赖操作系统的部分（std）去掉。 代价是：panic 时怎么办，要你自己给一个答案。这一节把 no_std 的组成与 panic 的真实体积讲清楚。

◷ 约 60 分钟◈ core vs std · panic_handler⚑ 体积敏感

3.1 core 与 std：留下什么、去掉什么

crate包含什么MCU 上
core语言内建能力：基本类型、Option/Result、切片、atomic、迭代器、fmt（可选）用（#![no_std] 后自动可用）
allocVec/Box/String：需要"堆分配器"需要时才引入（自己提供分配器或内存池）
std文件、网络、线程、std::io、panic=unwind… 依赖操作系统不用（除少数如 ESP32 带 OS 的场景）

关键点：no_std 不是"另一个 Rust"，它就是"把 std 换成 core"。大多数语言特性（所有权、trait、泛型、闭包、迭代器）都在 core 里，照常用。

3.2 panic_handler：panic 之后由你决定

std 在 panic 时会打印回溯并（可能）展开栈——这些都需要操作系统。no_std 下没有默认行为，所以编译器会要求你提供一个 #[panic_handler]，告诉它"panic 时做什么"。 嵌入式里最常见的答案就是"点个错误灯、复位、或直接死循环"。

min_no_std.rs — 最小 no_std 骨架（含 panic_handler 与入口） Rust 
// min_no_std.rs —— 一个能编过的最小固件骨架
#![no_std]
#![no_main]
use core::panic::PanicInfo;

#[panic_handler]
fn panic(_: &PanicInfo) -> ! { loop {} }   // 最小实现：死循环（现场可改成复位/灯闪）

static mut COUNTER: u32 = 0;

#[no_mangle]
pub extern "C" fn reset_handler() -> ! {
    unsafe { COUNTER = 0; }
    loop { unsafe { COUNTER = COUNTER.wrapping_add(1); } }
}

#![no_main] 表示"不要标准入口"；真正的入口（复位向量）通常由启动文件/连接脚本指向你导出的函数（这里示意为 reset_handler）。 这与第①册讲 STM32 启动流程时"Reset_Handler 里干了什么"是同一件事。

#[no_mangle]
pub static mut FAULT_CODE: u32 = 0;

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {

    loop { core::hint::spin_loop(); }
}
⚠ HardFault ≠ panic

panic 是软件主动触发的不可恢复错误（断言失败、unwrap() 到 None）。 硬件异常（HardFault/BusFault）是CPU 触发的，走的是异常向量，不是 panic_handler。 第①册 Module 08 讲的那套（CFSR 逐位、栈帧冻结）在这里仍然适用——Rust 只是把"应用级不可恢复"的收尾标准化了。

3.3 panic 的代价：不是"有没有"，而是"带不带格式化"

panic 本身在 MCU 上是"可控的"（通常编译成 panic=abort：直接终止），但带格式化的 panic 会把 core::fmt 拖进来， 体积可能翻几倍。这是评估"能不能用 panic"时最该量的一件事。

embedded-hal 抽象

embedded-hal 是嵌入式 Rust 的"驱动接口标准"：上层驱动只依赖 trait，不依赖具体芯片。 这一节讲清 trait 分层（PAC → HAL → 驱动 → 应用），以及最关键的选型问题：泛型（编译期单态化）还是 dyn（运行期分派）。

4.2 trait：把"能做什么"写成接口

一个通用驱动只需要声明它"要什么能力"，而不关心底层是谁。下面是一个完全自定义的迷你 OutputPin（真实项目里用 embedded-hal 的版本）：

hal_traits.rs — 泛型驱动：为每种 P 生成一份代码 Rust 
// hal_traits.rs —— trait 抽象 + 泛型驱动
#![no_std]

pub trait OutputPin { fn set_high(&mut self); fn set_low(&mut self); }

pub struct Led<P: OutputPin> { pin: P }
impl<P: OutputPin> Led<P> {
    pub fn new(pin: P) -> Self { Self { pin } }
    pub fn on(&mut self) { self.pin.set_high(); }
}

pub struct GpioA { odr: u32 }
impl OutputPin for GpioA {
    fn set_high(&mut self) { self.odr |= 1; }
    fn set_low(&mut self) { self.odr &= !1; }
}
pub struct GpioB { odr: u32 }
impl OutputPin for GpioB {
    fn set_high(&mut self) { self.odr |= 2; }
    fn set_low(&mut self) { self.odr &= !2; }
}

// 两个具体类型 → 单态化出两份代码
#[no_mangle] pub extern "C" fn use_a() { let mut l = Led::new(GpioA { odr: 0 }); l.on(); }
#[no_mangle] pub extern "C" fn use_b() { let mut l = Led::new(GpioB { odr: 0 }); l.on(); }

泛型的好处是零开销：set_high 被内联，没有间接跳转。代价是单态化—— Led<GpioA> 与 Led<GpioB> 是两份独立代码（与第②册的模板膨胀同源）。

中断与并发

第①册用 volatile + 关中断保护 ISR↔主循环共享量；C++ 分册讲 std::atomic 与内存序。 Rust 的路线略有不同：用类型让"能安全共享的东西"与"不能的"分开，并在没有硬件原子的核（M0）上直接不给你那个方法。

5.3 反面：static mut 裸共享（能编过，没人拦）

不选 Atomic、直接用 static mut 也能"跑"，但它把安全的担子全交还给你——而且编译器不会再检查：

// 反面：不带原子/临界保护的共享 static mut —— 数据竞争
#![no_std]

◆ 为什么它"能编过"反而是坏事

unsafe 的含义是"编译器无法替你检查，正确性由你保证"。它会编过、可能长期正常，然后在某个优化等级或时序下偶尔出错。 这与 C 的处境一样，但至少 Rust 逼你显式写下 unsafe——让"这里有风险"在代码里可见、可审计， 而不是像 C 那样完全无声。所以纪律是：能用 Atomic/critical-section 就别用 static mut。
底层上，Rust 把"内部可变性"这一能力收进唯一的受控类型 UnsafeCell：Cell/RefCell/Mutex 都建立在它之上——不是任意类型都能内部可变，这正是共享可变安全可控的原因。

5.5 真实临界区：cortex_m::interrupt::free

M0 上没有 fetch_add，标准解法就是"进临界区（关中断）"。真实工程里用 cortex-m 的 interrupt::free：它接收一个闭包，执行期间关中断、返回后恢复—— 正是第①册 enter_critical()/exit_critical() 的类型化封装，且不会忘记恢复。

critical_free.rs — 真实关中断临界区（Cargo 工程） Rust 
// critical_free.rs —— 用 cortex-m 的临界区封装共享访问
#![no_std]
#![no_main]
use panic_halt as _;
use core::sync::atomic::{AtomicU32, Ordering};
use cortex_m::interrupt;
use cortex_m_rt::entry;

static COUNT: AtomicU32 = AtomicU32::new(0);

#[entry]
fn main() -> ! {
    loop {
        // 关中断执行闭包，返回后自动恢复；M0 上的读-改-写也放这里
        let snapshot = interrupt::free(|_cs| COUNT.load(Ordering::Relaxed));
        let _ = snapshot;
        core::hint::spin_loop();
    }
}
◆ 三个层次的选型（对应 §5.1）
  • 单次 load/store → 直接 AtomicU32（M0/M3 都行）。
  • 读-改-写 → M3 用 fetch_add；M0 用 interrupt::free（本节的写法）。
  • 多字节一致性 → 临界区内拷出快照，或双缓冲（与第②册 M06 的 release/acquire 对应）。

5.6 真实中断处理器与 Send/Sync

Module 06 · DMA 与所有权

DMA 与所有权

DMA 是嵌入式里最容易出"幽灵 bug"的地方：传输进行中，CPU 又去改了同一块缓冲，或者把缓冲移走/释放了。 C 里这靠约定与注释；Rust 的借用检查器能在编译期把"传输期间缓冲被改动/移动"直接拦下——这一节讲它到底保证了什么。

◷ 约 65 分钟◈ 借用检查器 vs DMA⚑ 静态保证缓冲不被移动

6.1 DMA 的经典 C bug

设一次 UART/SPI 的 DMA 发送：你启动 DMA，把缓冲地址交给外设；在传输完成前，某处代码又写了同一块缓冲， 于是线上发出的数据一半是旧的、一半是新的；更糟的是缓冲在栈上，函数返回后地址失效，DMA 还在读它。

C 里的坑后果Rust 靠什么拦
传输中改动被 DMA 读的缓冲发出去的数据被撕裂借用：传输期间持有 &buf，禁止再改
把栈上缓冲交给 DMA 后函数返回悬垂 DMA生命周期：缓冲必须活得比传输久
缓冲被 free 后 DMA 还在读读到已复用内存所有权：move 后原绑定失效

缓冲的使用权像"接力棒"：CPU 持可变借用 → 启动 DMA（借出只读）→ 传输结束（DmaTx 析构）→ CPU 收回可变借用。借出期间任何改动都会被编译器拦下。

6.2 借用检查器如何保证"传输期间缓冲不动"

把"一次 DMA 传输"做成一个持有缓冲借用的对象：只要这个对象还活着，它对缓冲的共享借用就一直有效， 于是任何可变借用/修改都会被拒绝。

dma_ok.rs — 传输期间借用缓冲（合法） Rust 
// dma_ok.rs —— 传输期间持有 buf 的共享借用
#![no_std]

pub struct DmaTx<'a> { buf: &'a [u8], active: bool }
impl<'a> DmaTx<'a> {
    pub fn start(buf: &'a [u8]) -> Self { Self { buf, active: true } }
    pub fn busy(&self) -> bool { self.active }
    pub fn len(&self) -> usize { self.buf.len() }
}

pub fn demo(buf: &mut [u8]) {
    buf[0] = 1;
    let tx = DmaTx::start(buf);   // 共享借用 buf；此后不能再可变借用
    while tx.busy() { /* 等 DMA 完成 */ }
    let _ = tx.len();
}

注意 demo 接收 &mut [u8]（可变借用）：在 buf[0] = 1 之后、启动 DMA 之前的修改是允许的； 一旦 DmaTx::start(buf) 借出共享引用，buf 在 tx 存活期间就不能再被写。

6.3 &'static mut：给 DMA 一块"活得够久"的缓冲

栈缓冲天然活不过函数；要让 DMA 安全使用，缓冲通常放在静态存储里。Rust 里取得一块唯一的静态缓冲需要一次 unsafe（ 因为 static mut 的别名要你自己保证），但之后就能把它当普通 &mut [u8] 安全使用：

dma_static.rs — 从静态存储取得一个唯一的可变缓冲 Rust 
// dma_static.rs —— 把静态缓冲"借出一次"，之后按普通引用用
#![no_std]

static mut DMA_BUF: [u8; 64] = [0; 64];

/// # Safety
/// 只能调用一次；调用方必须保证此后不再通过其他路径访问 DMA_BUF。
pub unsafe fn take_dma_buf() -> &'static mut [u8] {
    &mut *core::ptr::addr_of_mut!(DMA_BUF)
}

pub fn use_buf() {
    // 在初始化阶段调用一次（真实项目里用 OnceCell/单例封装）
    let buf = unsafe { take_dma_buf() };
    buf[0] = 0xAA;
}
⚠ unsafe 只在这里出现一次

take_dma_buf 里的 unsafe 是唯一的不安全点：它承诺"这块缓冲的唯一可变引用只发出去一次"。 一旦拿到 &'static mut [u8]，之后所有使用都是安全的——借用检查器接管，DMA 期间你改它就编译不过。 实战里用 critical-section 或 OnceCell 把这个"只发一次"封装起来（见 Module 07 的封装规范）。

6.4 一个提醒：DmaTx 的真实语义

上面的 DmaTx 是教学简化：真实 DMA 完成后要由中断置"完成"标志，并在完成后归还缓冲。 但无论细节如何，核心不变——用类型表达"缓冲的使用权现在在谁手上"： DMA 在用时，CPU 只有只读借用；传输结束、对象析构后，CPU 才拿回可变借用。这套"所有权随状态流转"的写法， 与第①册"明确谁是 buffer 的 owner"、第②册 M10 的"边界处类型擦除"是同一个工程直觉。

◆ 自测 · Module 06（先答再看）

  1. 简答：Rust 如何在不运行时检测的情况下，保证"DMA 传输期间缓冲不被改"？

    传输对象持有缓冲的共享借用；只要该对象活着，缓冲就被借用，任何可变借用/修改都会在编译期被拒绝（E0506）。

  2. 判断：把栈上的 [u8; N] 交给 DMA 也不会有问题，因为 Rust 很安全。

    不对。栈缓冲在函数返回后失效，DMA 若仍在读就是悬垂——生命周期检查会阻止你把一个"活不够久"的借用传进要求更长生命周期的位置。DMA 缓冲应放静态存储。

Module 07 · unsafe 与 FFI

unsafe 的边界与 FFI

Rust 的"安全"不是"没有 unsafe"，而是"不安全的地方少、且都看得见"。 寄存器读写、DMA、与 C 库互调，都离不开 unsafe。这一节讲什么时候必须 unsafe、如何把它封装成安全 API，以及 extern "C" 互操作。

◷ 约 70 分钟◈ 安全封装 · extern "C"⚑ 边界必须收敛

7.1 什么时候必须 unsafe

必须 unsafe 的操作嵌入式里的场景
解引用裸指针MMIO 寄存器读写、访问固定地址
调用 extern "C" 函数用现成的 C 库 / HAL / RTOS API
访问/修改 static mut唯一的静态共享缓冲（Module 06）
实现 unsafe trait把"我的类型满足某个不变量"告诉编译器（如自实现 Send）

unsafe 不关闭借用检查、不做任何优化取舍——它只是把"这处不变量由人保证"标出来。所以纪律不是"消灭 unsafe"，而是收敛它。

FIG 7.1 unsafe 边界：不安全收敛在一层薄薄的"叶子"
目标不是"没有 unsafe"，而是让它薄且集中：上层全是安全代码，unsafe 只在叶子层、每处写清契约，出问题时的审查范围极小。

7.2 封装规范：把 unsafe 关进一个安全函数

正确做法：只在最底层出现一次 unsafe，外面暴露一个安全 API，并用文档注明安全契约。 典型例子——把一个寄存器地址包成"可安全读取"的类型：

unsafe_wrap.rs — 安全 API 包住唯一的 unsafe Rust 
// unsafe_wrap.rs —— 用安全 API 包住一处必要的不安全
#![no_std]

pub struct Mmio { addr: *const u32 }
impl Mmio {
    pub fn new(addr: u32) -> Self { Self { addr: addr as *const u32 } }
    /// 安全契约：addr 必须是有效的只读寄存器地址（由 `new` 的调用方保证）
    pub fn read(&self) -> u32 {
        unsafe { core::ptr::read_volatile(self.addr) }   // 唯一的不安全点
    }
}

pub fn read_sensor() -> u32 { Mmio::new(0x4001_2000).read() }
◆ 一条可操作的封装规范
  • unsafe 只出现在叶子函数：上面的 read 是叶子；调用方 read_sensor 完全安全。
  • 为一个 unsafe 写清"安全契约"：满足什么条件才能安全调用（这里是"地址有效"）。
  • 用类型缩小契约范围：Mmio::new(addr) 把"地址由谁保证"集中到一处，而不是处处强转。

7.3 与 C 互调：extern "C" 与 #[no_mangle]

两件事要分清：调用 C（声明外部符号，调用处 unsafe）与导出给 C（#[no_mangle] pub extern "C"，关闭名字修饰）。 这与第②册 M09 讲 C++ 的 extern "C" 是同一套链接规则。

异步固件、取消与外设所有权

说明异步取消后 DMA 缓冲区何时可以安全归还。

前置：本册前面的类型、函数与资源管理阅读约 15–25 分钟；实践约 30–60 分钟（规划估计）

机制与契约

Transfer 同时独占借用 Channel 与缓冲，存在期间调用者不能再次使用它们。Drop 可实现清理，但真实 DMA 是独立于 CPU 的外设：丢弃 Future 后，硬件仍可能继续读写内存。实际取消协议必须禁止新提交、停止通道、等待硬件确认静止、清除/屏蔽晚到中断，再归还缓冲与外设所有权。示例只实现同步停止的 mock，验证借用与再次提交；不把软件 busy=false 视作硬件停止证据。

{ let mut transfer=channel.start(&mut buffer);
  transfer.mock_progress(); } // mock 在 Drop 同步停止

边界与误用

只在 Drop 写一个标志不足以停止 DMA；异步等待不能直接放进普通 Drop。可采用显式 async cancel_and_wait，或满足同步停止保证的硬件抽象，并规定强制掉弃时的安全策略。

术语

术语含义
所有权每个值有且只有一个所有者；所有者离开作用域即析构。它是 Rust 消灭"忘记释放/重复释放"的根机制。
借用不转移所有权的临时引用：&T 为共享借用（可多个、只读），&mut T 为独占借用（同时只能一个）。
生命周期引用必须不晚于它引用的数据失效；用 'a 显式标注，对应 C 里的悬垂指针约束。
类型状态机把"对象处于哪个状态"编码进类型（如 Uart<Uninit> / Uart<Ready>），使"前置条件未满足"的操作根本不存在。
newtype只用一层包装区分同一底层类型的不同含义（如 struct RegAddr(u32)），运行期零开销。
no_std去掉依赖操作系统的 std，只用 core；需自备 panic 行为、入口（可选分配器）。
coreRust 语言内核 crate：基本类型、Option/Result、切片、atomic、迭代器、fmt（可选）。
panic_handlerno_std 下由你提供的"panic 时做什么"的函数（#[panic_handler]）；缺失则可执行 crate 构建失败。
UnsafeCellRust 中唯一允许"内部可变性"的底层类型；Cell/RefCell/Mutex 等都建立在它之上。共享可变的根源难点都在这里。
SendT 的所有权可安全转移到另一执行单元；跨上下文传递值的编译期约束。
Sync&T 可安全跨执行单元共享；因此 static T 要求 T: Sync。这是"无数据竞争"的类型来源。
单态化泛型在编译期为每种具体类型各生成一份代码（monomorphization）；零运行时开销，代价是体积膨胀。

符号 / 构件

符号 / 构件类别说明
#[entry]宏（cortex-m-rt）标记复位后进入的 main；由 cortex-m-rt 生成启动与调用序列。
#[exception]宏（cortex-m-rt）注册系统异常处理器（SysTick / HardFault / …）。
#[interrupt]宏（PAC）注册外设中断处理器（中断名来自具体芯片 PAC）。
#[no_mangle]属性关闭名字修饰，导出稳定的 C 符号名（供 C/汇编/向量表使用）。
extern "C"ABI 约定使用 C ABI 与链接名；声明外部 C 函数或导出 Rust 函数。
Reset符号（cortex-m-rt）复位向量指向的符号：清 .bss、调用 __cortex_m_rt_main 最终进 main。
HardFault_符号（cortex-m-rt）默认硬故障处理器（未自定义时的兜底）。
__INTERRUPTS符号（链接）中断向量表区域；由 cortex-m-rt 依据 memory.x 与向量布局生成。
memory.x文件（链接脚本片段）声明 Flash/RAM 的 ORIGIN 与 LENGTH，被链接脚本 link.x 引用。
critical-sectioncrate/机制跨平台"临界区"抽象；cortex-m 提供 interrupt::free / single-core 实现。
panic-haltcrate现成的 panic_handler：panic 后死循环，省去自己实现。
