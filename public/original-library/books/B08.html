1.2 真实证据：显式状态机

下面这段主机程序验证状态机的故障锁存、非法事件忽略与显式复位：

/* host_fsm.c —— 应用状态机：正常/降级/故障锁存（主机可运行）。 * * 把界面的“模式”与业务的“状态”统一成一张显式状态机： *   BOOT → IDLE → RUN →（STOP）IDLE；RUN 遇 SENSOR_INVALID → FAULT（锁存）。 * 关键规则：① 故障优先并锁存，必须显式 RESET 才能清除；② 非法的 (状态,事件) 组合被忽略，不改变状态。 * * 编译运行：gcc -std=c11 -Wall -Wextra -O2 host_fsm.c -o host_fsm && ./host_fsm */#include <stdio.h>#include <string.h>typedef enum { BOOT, IDLE, RUN, FAULT, SLEEP, NSTATE } state_t;typedef enum { EV_START, EV_ARM, EV_STOP, EV_SENSOR_INVALID, EV_RESET, EV_SLEEP, EV_WAKE, NEVENT } event_t;static const char *SNAME[NSTATE]  = {"BOOT", "IDLE", "RUN", "FAULT", "SLEEP"};static const char *ENAME[NEVENT]  = {"START", "ARM", "STOP", "SENSOR_INVALID", "RESET", "SLEEP", "WAKE"};/* 返回下一个状态；无效组合返回当前状态 */static state_t step(state_t s, event_t e) {    switch (s) {        case BOOT:  return (e == EV_START) ? IDLE : s;        case IDLE:  if (e == EV_ARM) return RUN;                    if (e == EV_SLEEP) return SLEEP;                    return s;        case RUN:   if (e == EV_STOP) return IDLE;                    if (e == EV_SLEEP) return SLEEP;                    if (e == EV_SENSOR_INVALID) return FAULT;   /* 故障优先且锁存 */                    return s;        case FAULT: return (e == EV_RESET) ? IDLE : s;          /* 只能显式复位 */        case SLEEP: return (e == EV_WAKE) ? IDLE : s;        default:    return s;    }}int main(void) {    event_t script[] = {EV_START, EV_ARM, EV_SENSOR_INVALID, EV_ARM, EV_RESET, EV_ARM};    state_t s = BOOT;    int entered_fault = 0, ignored_in_fault = 0;    printf("起始状态: %s\n", SNAME[s]);    for (unsigned i = 0; i < sizeof(script) / sizeof(script[0]); i++) {        state_t ns = step(s, script[i]);        printf("  %-14s: %s -> %s%s\n", ENAME[script[i]], SNAME[s], SNAME[ns],               ns == s ? "（忽略）" : "");        if (ns == FAULT) entered_fault = 1;        if (s == FAULT && ns == FAULT) ignored_in_fault++;        s = ns;    }    printf("最终状态: %s\n", SNAME[s]);    int ok = 1;    if (!entered_fault) ok = 0;          /* 故障被进入 */    if (ignored_in_fault < 1) ok = 0;    /* 锁存：FAULT 期间的 ARM 被忽略 */    if (s != RUN) ok = 0;                /* 复位并重新 ARM 后回到 RUN */    if (step(IDLE, EV_SENSOR_INVALID) != IDLE) ok = 0;  /* IDLE 下该事件无效 */    printf("\n%s\n", ok ? "RESULT: PASS" : "RESULT: FAIL");    return ok ? 0 : 1;}

1.5 常见误区与排障

失败路径与排障
  • 没有量化需求就选架构：要么过度设计，要么不够用。
  • 没有状态机：模式切换散落各处 if，故障时行为不可预测。
  • 故障不锁存：传感器自恢复后自动继续输出，可能把错误带进执行器。
  • 接口未定义：模块互相直接调用，替换/测试困难。
◆ 自测 · Module 01（先答再看）

  1. 传感器瞬时无效，为什么状态机应进入 FAULT 而不是自动回到 RUN？

    查看答案

    瞬态异常往往意味着更深的问题；自动恢复可能让错误在执行器上被放大。正确做法是进入安全态并锁存，等显式复位或人工确认后再恢复。

  2. “采样率/续航/响应”为什么必须先量化？

    查看答案

    它们直接决定架构（是否需要周期任务、低功耗策略、优先级分配）。不量化就只能凭感觉选，容易过度设计或不够用。

  3. 模块为什么统一成 {init, poll/task} 接口？

    查看答案

    接口统一后，前后台与 RTOS 只是“谁来调用”的实现差异，模块可独立替换与测试；否则互相直调、耦合加深。

  1. “上报周期”应放编译期宏还是运行期参数？

    查看答案

    运行期参数。现场可能因网络/功耗需要调整，写死宏意味着每次重烧；但它应有合法范围与默认值，并持久化可回退。

    查看答案

    上层要据此决定“重试、降级还是复位”。参数错要纠正输入、IO 错可重试、硬件错需复位；若只返回 0/1 就无法决策。

    宏改动需重编译（用于功能裁剪、引脚），运行期参数必须能在现场存改并回退（阈值/标定）。混在一起会让现场不可调、版本不可控。

◆ 自测 · Module 03（先答再看）

  1. 为什么“两次短按间隔”要用时间阈值区分双击与两次单击？

    查看答案

    没有间隔阈值就无法区分“用户想双击”还是“连按两下”。阈值太小会误判双击，太大则单击响应变慢；常在 250~300ms 折中。

  2. 菜单为什么用栈而不是散落状态变量？

    查看答案

    栈天然表达层级：进入压栈、返回出栈，逻辑清晰且可嵌套；散落变量在层级加深后容易出错。

  3. 参数修改后为什么必须立即持久化？

    查看答案

    否则掉电丢失，用户会以为“设置无效”。持久化要配合双副本/CRC（M13）以防半写损坏。

  1. 为什么提交标记要用“擦除态→魔数”（只把 1 写成 0）？

    查看答案

    Flash 只能把位从 1 写成 0，擦除才能回到 1。用擦除态（全 1）表示未提交、魔数表示已提交，只需一次写 0 即可置位，掉电也不会产生中间态。

    查看答案

    反过来的话，掉电可能留下“已提交但数据不全”的记录，恢复时会把垃圾当有效。先写数据后提交，掉电最多丢未提交的最后一条。

  3. 采集为什么不用循环忙等？

    查看答案

    忙等时基随其它任务负载漂移，采样率不稳。应用定时器或周期任务产生固定周期，并统计采样间隔的最坏值。

◆ 自测 · Module 10（先答再看）

  1. 采集与显示共用 I²C，谁先谁后？

    查看答案

    不是“谁先谁后”，而是用互斥量保证同一时刻只有一个事务；采集优先级更高，拿不到锁时短等或直接跳过本次显示刷新，不能阻塞采集截止期。

  2. 为什么每个关键调用都要有超时？

    查看答案

    某个外设/网络无响应时，无超时会卡死整条链；有超时才能降级、重试或跳过，保持系统可用。

  3. 升级任务为什么设低优先级？

    查看答案

    升级是“能慢不能断”的批量活。低优先级让业务随时抢占它，避免长下载挤占采样/控制导致实时性破坏或看门狗超时。

◆ 自测 · Module 13（先答再看）

  1. 为什么读参数要“选最新有效的一份”，而不是固定读 A？

    查看答案

    写入可能在 A 完成、在 B 中断；固定读 A 会读到旧值或坏值。应比较两份版本号并各自校验 CRC，取“校验通过且版本最新”的才正确。

  2. 参数版本升级为什么要配迁移函数？

    查看答案

    新固件可能读到旧结构（缺字段），旧固件可能读到新结构。迁移函数按默认值补齐/转换，使配置在升级时仍可用。

  3. 为什么坏参数绝不能作为有效值使用？

    查看答案

    否则故障会变得“看得懂却解释不了”，且每次重启行为不一致，极难定位。双副本+CRC+默认回退保证任一时刻都返回自洽参数。

14.5 常见误区与排障

失败路径与排障
  • 界面直接改业务变量：状态来源多，冲突无法追踪。
  • 无脑全屏刷新：总线/CPU 被刷屏占满，挤占采样与控制。
  • 刷新与状态不同步：显示出现中间态或跳变。
  • 换屏就改业务：驱动与逻辑未分层，移植成本高。
◆ 自测 · Module 14（先答再看）

  1. 为什么“脏标志”能同时改善功耗与实时性？

    查看答案

    无变化时跳过刷新，减少总线传输与 CPU 开销；省下的时间/电量可用于采样与控制，间接改善实时性与续航。

  2. 为什么渲染函数不能反向修改业务状态？

    查看答案

    否则状态来源多、出现隐藏副作用，冲突无法追踪且难以测试。渲染只读，业务只改状态，边界清晰。

  3. 事件驱动的界面为什么事件队列要有界？

    查看答案

    无界队列在事件风暴下会吃光 RAM。有界并在满时合并/丢弃（带计数）才安全。

  1. 为什么“可维护性”也算产品验收项？

    查看答案

抗饱和 (Anti-windup)

微分先行
对测量值而非误差微分，避免设定值阶跃时微分冲击。
上报策略
周期/变化触发/批量；按带宽、功耗与实时性权衡。

平均电流 = Σ(工作电流 × 占空比)；据此估算续航。
