为什么嵌入式学 C++ 值得，但必须"按账单学"

C++ 能带来零开销抽象：RAII 自动释放、模板编译期分派、constexpr 把计算搬到编译期 —— 这些都是 C 里要手写且容易出错的。 但它的每一项特性都有明确的代价：异常与 RTTI 会带来体积和运行时开销，iostream 在 MCU 上几乎不可接受，动态多态在 M0 上每次调用都更贵。 本册的立场是：不拒绝 C++，也不无条件推荐 —— 每一项都先算清账单，再决定用不用。

⚠ 先破除两个直觉
  • "C++ 一定比 C 大"是错的：这张表里 C++ 版（40 字节）反而比 C 版（68 字节）小。 但真正的原因不是"C++ 内联更好"，而是发射口径不同：C 版的 uart_write 是外部函数， 即使这个 TU 里没人调用它，.o 里也会被发射（nm drv_c.o 能看到它）； C++ 版的 Uart::write 是类内定义的隐式 inline 函数，本 TU 未引用，就根本不发射。 换成把 C 版 uart_write 标成 static，两者立刻持平。差异是几字节级的，且可正可负。
  • "虚函数一定贵"也不成立：这个微例里虚调用（6 字节）比函数指针表（10 字节）还小。 所以"贵不贵"不能背结论，只能按场景测。

1.2 编译开关：把不需要的东西关掉

真正拉开差距的不是"用不用 C++"，而是用它的时候开没开对开关。 嵌入式 C++ 的第一条纪律就是：把标准默认打开的、你不需要的运行时设施全部关掉。

开关关掉什么为什么嵌入式要关
-fno-exceptions异常（throw/catch）异常需要展开表（unwind tables）与运行时代码，只在抛出时才跑、但代码与表一直在；MCU 上通常不需要
-fno-rtti运行期类型信息dynamic_cast/typeid 要额外的类型描述表；用不到就别编进去
-fno-threadsafe-statics函数内 static 的线程安全初始化默认会给每个函数内静态量加一个"守卫变量 + 原子检查"；单线程中断模型下不需要
-fno-use-cxa-atexit全局对象析构的登记避免为"退出时析构"引入 __cxa_atexit（而裸机根本不会退出）
-fno-unwind-tables
-fno-asynchronous-unwind-tables		栈回溯表不为"异常/回溯"生成额外表；需要 bt 回溯时再单独权衡
-fno-common把重复定义合并成 COMMON与 C 一致：重复定义要报错，而不是静默合并（GCC 10+ 已默认）
-Os + -flto—体积优先；LTO 能跨 TU 内联与删死代码（代价是编译变慢）
-Wall -Wextra -Wold-style-cast—把 C 风格强制转换、隐式截断等问题尽早暴露（与第①册同一套警告纪律）
✔ 一条工程惯例

把这组开关写进 Makefile/CMake 的公共 CXXFLAGS，而不是"记得的时候加"。 本册后面所有示例都默认带 -fno-exceptions -fno-rtti； 当某一节需要讨论"开了会怎样"时，会显式注明。

一个容易忽略的点：-fno-exceptions 只作用于你自己编译的代码。 预编译的 libstdc++/libstdc++_nano 仍然是带异常构建的； 若你用到内部可能 throw 的组件（例如 std::function 的某些分配路径）， 仍可能被牵回异常运行时 —— 这也是 Module 05 讨论 std::function 时要当心的原因。

1.3 逐项算账

1.3.1 异常（exceptions）

异常的核心代价不在"抛"的时候，而在"编译器必须为'随时可能抛'准备数据"： ARM 上 GCC 用的是表驱动的"零成本"异常模型 —— 正常执行路径上不会为每条指令插入检查或簿记（这才是"零成本"的含义）， 代价集中在只读的展开表（.ARM.exidx/.ARM.extab）与异常运行时本身。 本机实测：同一份驱动，-fno-exceptions 是 40 字节，显式 -fexceptions 变成 48 字节 —— 这多出的 8 字节基本就是新增的 .ARM.exidx（size 把只读表也算进 text）； 真正的运行时（libgcc 的 unwind、terminate handler）在链接后才出现，远不止 8 字节。

⚠ 嵌入式里用异常的三条硬约束
  • 不能跨中断边界抛：ISR 与线程/主循环是不同的栈上下文，异常无法安全穿越。
  • 需要 unwinder 与 __exidx：裸机链接常因缺 __exidx_start/__exidx_end 或终止处理而失败。
  • 最好的做法往往是"不用异常，用错误码"：这与第①册 Module 07 的 err_t 体系一脉相承。

1.3.2 RTTI

dynamic_cast 与 typeid 依赖运行期类型描述表。 嵌入式里几乎不用它们（多态靠虚表已经够），所以 -fno-rtti 基本是默认动作。 关掉之后，dynamic_cast/typeid 会直接编译报错 —— 这也是好事，能拦住误用。

1.3.3 iostream：在 MCU 上的真实账单

这是最"教科书级"的一个坑。#include <iostream> 看着无害，但把 std::cout << "hello\n"; 放进一个空程序之后，编译过、链接不过： 本机实测报 12 处未定义引用。

未定义符号（实测去重后共 11 个）它来自哪儿
_write / _read / _close / _lseek / _open / _fstat / _isattynewlib 的文件/终端 syscall 桩 —— cout 最终要落到 _write
_sbrk堆边界；缓冲区申请可能走到它
_exit / _kill / _getpid进程收尾与信号（exit/abort 路径）

这里要先纠正一个常见的误传："链接失败"这件事，跟 locale / 宽字符无关。 12 条报错里没有一条是 swprintf/getwc 之类的宽字符符号，清一色是 newlib 的 syscall 桩 —— 换句话说，链接失败只是"缺桩"，补上就能链过。 但链过之后的体积膨胀是另一回事：那才是 libstdc++ 的 iostream / locale 机制被真正拉进镜像的结果（见下）。

所以真正的问题不是"链不过"，而是链过之后有多大：

1.3.4 动态分配、虚函数、模板

1.4 一份对照实验：同一功能，C 与 C++

下面两份代码功能等价：一个 UART 发送 + 一个 CRC8。左边是 C，右边是 C++（成员函数 + 构造函数）。 它们都能通过本册的编译门禁；本机 size 结果就是 §1.1 那张表。

drv_c.c — C 版：结构体 + 函数 C 
/* drv_c.c —— C 的写法：数据（uart_t）与操作（uart_write）是分开的 */
#include <stdint.h>

typedef struct { uint32_t base; uint8_t id; } uart_t;

static uint8_t crc8(const uint8_t *d, uint32_t n)
{
    uint8_t c = 0;
    while (n--) {
        c ^= *d++;
        for (int i = 0; i < 8; i++) c = (uint8_t)((c << 1) ^ ((c >> 7) * 0x07));
    }
    return c;
}

void uart_write(uart_t *u, const uint8_t *buf, uint32_t n)
{
    volatile uint32_t *p = (volatile uint32_t *)u->base;
    while (n--) {
        while (!(p[0] & 0x80)) { }   /* SR(0x00) 的 TXE 位(bit7) */
        *(volatile uint8_t *)(u->base + 4) = *buf++;
    }
}

uint8_t frame_crc(const uint8_t *b, uint32_t n) { return crc8(b, n); }
drv_cpp.cpp — C++ 版：数据与操作封装在一起 C++ 
// drv_cpp.cpp —— C++ 的写法：构造即绑定，<cstdint> + class
#include <cstdint>

class Uart {
public:
    constexpr Uart(uint32_t base, uint8_t id) : base_(base), id_(id) {}
    void write(const uint8_t *buf, uint32_t n) const {
        volatile uint32_t *p = reinterpret_cast<volatile uint32_t *>(base_);
        while (n--) {
            while (!(p[0] & 0x80)) { }   /* SR(0x00) 的 TXE 位(bit7) */
            *reinterpret_cast<volatile uint8_t *>(base_ + 4) = *buf++;
        }
    }
private:
    uint32_t base_;
    uint8_t  id_;
};

static uint8_t crc8(const uint8_t *d, uint32_t n)
{
    uint8_t c = 0;
    while (n--) {
        c ^= *d++;
        for (int i = 0; i < 8; i++) c = (uint8_t)((c << 1) ^ ((c >> 7) * 0x07));
    }

Module 02 · 类与 RAII

类、封装与 RAII

第①册 Module 07 用"不透明指针 + 成对的 init/deinit"在 C 里模拟了封装。 C++ 把这件事做成了语言的一部分：构造即获取、析构即释放。 这一节讲清它替掉了什么、代价是什么，以及嵌入式里最该用它的两处。

◷ 约 75 分钟◈ Rule of 0/3/5⚑ 全册最实用的一节

2.1 从"成对的调用"到"一对构造/析构"

C 里每个资源（GPIO、串口、锁、DMA 通道）都遵循同一套模式：xxx_init() 获取、xxx_deinit() 释放。 问题在于编译器不知道它们是一对：忘了 deinit、提前 return、在两条分支里漏掉一条 —— 都不会报错，只会在运行期表现为"资源泄漏 / 外设不恢复"。

C 的成对调用C++ 的 RAII谁保证配对
gpio_init(&pin); … gpio_deinit(&pin);构造 GpioPin … 离开作用域自动析构编译器（作用域退出时必调析构，含提前 return）
uint32_t s = enter_critical(); … exit_critical(s);作用域内建一个 IrqLock编译器
分配/释放缓冲区一个持有者对象（含移动语义）编译器（对象销毁即释放）
◆ RAII 的名字就是它的全部含义

Resource Acquisition Is Initialization： 把"获取资源"放进构造函数、把"释放资源"放进析构函数。 只要对象是栈上的局部变量，任何**正常**的离开作用域（包括提前 return）都会调用析构。 注意"正常"二字 —— C++ 里唯一能绕过析构的是 longjmp/硬件异常这类"非正常退出"，而嵌入式正好常遇到它们（见 §2.6）。

FIG 2.1 手动配对 vs RAII：遇到"提前 return"时谁还记得释放
C：提前 return 时若没手动调 deinit()，资源就泄漏了——编译器不会提醒。 C++ RAII：只要对象是局部变量，任何正常离开作用域（含提前 return）都会自动调用析构。

2.2 封装：不透明指针 vs 类

第①册的 C 版把结构体定义藏在 .c 里、头文件只留 typedef struct sensor sensor_t;。 C++ 的类默认就是这种"接口与实现分离"：private 成员对使用者不可见、不可直接访问，由编译器强制。

2.3 RAII 包装一个 GPIO 引脚

下面左边是 C 的典型写法（init/deinit 配对），右边是等价的 RAII 类。 注意 C++ 版：构造时配置、析构时恢复，而且拷贝被显式删除（一个引脚不应该有两个"主人"）。

gpio_c.c — C：手动配对，漏了就出问题 C 
/* gpio_c.c —— 谁调用 gpio_deinit，谁负责；编译器不检查 */
#include <stdint.h>
typedef struct {
    volatile uint32_t crl, crh, idr, odr, bsrr;   /* STM32F1 GPIO 寄存器 */
} gpio_regs_t;

static void gpio_init(gpio_regs_t *g, uint8_t pin, int as_output)
{
    if (!as_output) return;                       /* ✕ 早退分支漏掉"已初始化"的标记 */
    volatile uint32_t *cfg = (pin < 8u) ? &g->crl : &g->crh;
    const uint32_t sh = (pin & 7u) * 4u;
    *cfg = (*cfg & ~(0xFu << sh)) | (0x1u << sh);    /* CNF=00, MODE=01：通用推挽输出 */
}
static void gpio_deinit(gpio_regs_t *g, uint8_t pin)
{
    volatile uint32_t *cfg = (pin < 8u) ? &g->crl : &g->crh;
    const uint32_t sh = (pin & 7u) * 4u;
    *cfg &= ~(0xFu << sh);                           /* 复位为模拟输入 */
}
void use_gpio(gpio_regs_t *g, uint8_t pin, int fail_early)
{
    gpio_init(g, pin, 1);
    if (fail_early) return;                        /* ✕ 提前 return → 忘了 deinit */
    g->bsrr = (1u << pin);                         /* BSRR：单次写即置位，无需读改写 */
    gpio_deinit(g, pin);
}
gpio_raii.hpp — C++：构造获取、析构释放、禁拷贝 C++ 
// gpio_raii.hpp —— 把"配置一个引脚"变成一个对象的生命周期
#include <cstdint>

struct gpio_regs { volatile uint32_t crl, crh, idr, odr, bsrr; };   /* STM32F1 GPIO */

class GpioPin {
public:
    GpioPin(gpio_regs* r, uint8_t pin) noexcept : r_(r), pin_(pin) {}

    void as_output() noexcept {
        volatile uint32_t* cfg = (pin_ < 8u) ? &r_->crl : &r_->crh;
        const uint32_t sh = (pin_ & 7u) * 4u;
        *cfg = (*cfg & ~(0xFu << sh)) | (0x1u << sh);  // CNF=00, MODE=01
        owned_ = true;
    }
    void set(bool on) noexcept {
        // BSRR 低 16 位置位、高 16 位复位：单次写即原子，不必读改写 ODR
        r_->bsrr = on ? (1u << pin_) : (1u << (pin_ + 16u));
    }

    ~GpioPin() {
        if (owned_) {
            volatile uint32_t* cfg = (pin_ < 8u) ? &r_->crl : &r_->crh;
            const uint32_t sh = (pin_ & 7u) * 4u;
            *cfg &= ~(0xFu << sh);
        }
    }

    // 一个引脚只能有一个主人：拷贝被删除，回头要用"移动"（§2.5）
    GpioPin(const GpioPin&) = delete;
    GpioPin& operator=(const GpioPin&) = delete;

private:
    gpio_regs* r_;
    uint8_t    pin_;
    bool       owned_ = false;
};

void use_gpio(gpio_regs* r, uint8_t pin, bool fail_early)
{
    GpioPin p(r, pin);
    p.as_output();
    if (fail_early) return;      // ✔ 提前 return 也会调用 ~GpioPin()
    p.set(true);
}
✔ 代价与收益

2.4 Rule of 0 / 3 / 5：什么时候要自己写

一个类要不要自己写拷贝/移动/析构，取决于它是否直接管理资源。这条经验法则就叫 Rule of 0/3/5：

法则适用做法
Rule of 0类里不直接持有裸资源（只组合已有类型）什么都不写，让编译器生成——最理想的默认
Rule of 3需要自定义析构（说明持有资源）析构 + 拷贝构造 + 拷贝赋值三者要么都写、要么都禁
Rule of 5还想支持"搬走"资源在 3 的基础上再加移动构造 + 移动赋值
只想禁拷贝独占资源（引脚、锁、DMA 通道）= delete 掉拷贝，需要传递时用移动
⚠ 最常见的坑：删了拷贝，却忘了"移动"

= delete 掉拷贝构造后，这个类型就不能拷贝、也不能放进容器（vector 扩容要拷贝或移动）。 但要注意：按值返回一个"纯右值"并不需要拷贝或移动 —— C++17 起保证复制省略（guaranteed copy elision）， return ByteStream(mem, cap); 是就地构造；只有"返回具名局部变量"（NRVO 不保证）才需要移动。 嵌入式里更常见的做法是：让资源拥有者不被传递（就地构造），或者给它一个明确的移动语义（下一节）。

✔ = default 与 = delete：把"我要什么"写清楚

= delete 明确禁掉某个特殊成员（如拷贝）；= default 明确用编译器生成的默认实现。 两者都比"不写"更清楚：不写时读者要猜"是默认了，还是漏了"。
三条最容易踩的相互抑制规则：

  • 声明任一拷贝操作 → 另一个拷贝操作与两个移动操作都不再隐式声明；
  • 声明任一移动操作 → 两个拷贝操作被隐式声明为 = delete（仍参与重载，直接报错，而不是悄悄消失）；
  • 声明析构函数 → 两个移动操作不再隐式声明 —— 这正是"写了析构却忘了移动"的高频坑。

所以直接管理资源时，把 = default/= delete 逐条显式写出来，避免被抑制后得到意外行为。 注意 = default 只在能生成出正确语义时用；对直接管理裸资源的类，默认的按成员拷贝往往是错的（那才是 Rule of 3 要自己写的原因）。

2.5 移动语义：把资源"搬走"，而不是"复制"

移动（move）不是一个新东西，它是"转移所有权"的标准表达：源对象把资源交出去后进入"空"状态。 对固定缓冲/句柄来说，移动只需搬几个指针/长度，不复制底层数据。

stream.hpp — 移动语义：移交缓冲所有权 C++ 
// stream.hpp —— 一个"拥有"一段缓冲的写入流；移动而不是拷贝
#include <cstdint>

class ByteStream {
public:
    ByteStream(uint8_t* buf, uint32_t cap) noexcept : buf_(buf), cap_(cap) {}

    // 移动：把 buf_/cap_/len_ 接管过来，把源置空
    ByteStream(ByteStream&& o) noexcept : buf_(o.buf_), cap_(o.cap_), len_(o.len_) {
        o.buf_ = nullptr; o.cap_ = 0; o.len_ = 0;
    }
    ByteStream& operator=(ByteStream&& o) noexcept {
        if (this != &o) {
            buf_ = o.buf_; cap_ = o.cap_; len_ = o.len_;
            o.buf_ = nullptr; o.cap_ = 0; o.len_ = 0;
        }
        return *this;
    }

    ByteStream(const ByteStream&) = delete;             // 独占：不许拷贝
    ByteStream& operator=(const ByteStream&) = delete;

    bool push(uint8_t b) noexcept { if (len_ >= cap_) return false; buf_[len_++] = b; return true; }
    uint32_t size() const noexcept { return len_; }
    bool valid() const noexcept { return buf_ != nullptr; }

private:
    uint8_t* buf_;
    uint32_t cap_;
    uint32_t len_ = 0;
};

// 用法：工厂函数"按值返回"一个流 —— 靠移动，没有数据拷贝
ByteStream make_stream(uint8_t* mem, uint32_t cap) {
    return ByteStream(mem, cap);        // C++17 起：保证省略拷贝（RVO/隐式移动）
}
◆ 移动语义在嵌入式里的意义

台式机上移动是为了"避免复制大对象"。在 MCU 上，它的价值更偏向表达所有权： 让"这段缓冲归谁"变成类型系统里的事实（只能有一个 ByteStream 持有它）， 从而在编译期排除"两个对象都想释放同一块内存"。这与第①册反复强调的"所有权清晰"是一回事。

2.6 析构不会在哪些情况下运行（嵌入式必读）

RAII 的保证建立在"作用域正常退出"之上。嵌入式中下面这些"非正常退出"会绕过析构，必须单独处理：

函数正常返回 / 提前 return会RAII 的主战场
break/continue/goto 跳出作用域会编译器正确插入析构

HardFault / 未定义指令等硬件异常不会栈帧就地冻结，析构完全不执行 → 资源停留在中间态

◆ 析构顺序：后构造的先析构（嵌套 RAII 的基石）
  • 局部对象：按构造的逆序析构（栈式）—— 先建的锁、外层缓冲最后才释放。
  • 成员：按声明顺序的逆序析构（初始化是声明顺序，析构反过来；与构造函数的初始化列表书写顺序无关）。
  • 基类：所有成员析构完之后，才析构基类。
  • 收益：只要按"依赖关系"声明/构造，销毁顺序自动正确 —— 依赖者先建、后被销毁；被依赖者后建、先销毁。
✔ 嵌入式里的经典用法

先构造 IrqLock（关中断）、再构造 SpiBus（用总线抽数据）； 离开作用域时，SpiBus 先析构（总线用完），IrqLock 后析构（再开中断） —— 这正是手写 exit_critical() 时最容易写反的顺序。

⚠ 推论：RAII 管"软件资源"，管不了"硬件异常与复位"

所以嵌入式里 RAII 用来说明"正常控制流下的资源生命周期"（引脚、锁、缓冲、会话）， 而"断电/复位/崩溃后的恢复"要靠第①册 Module 08 的那套机制（看门狗、复位原因、备份寄存器、上电自检）。 两者分工明确，不能互相替代。

  1. 简答：RAII 相比 C 的 init/deinit 配对，核心优势是什么？

    把"释放"绑定到对象生命周期上：只要对象是栈局部变量，任何正常离开作用域（含提前 return）都会触发析构。这消除了 C 里最常见的"某条分支忘了释放"。

    不行。写了析构通常意味着"持有资源"（Rule of 3）：要么同时定义/删除拷贝构造与拷贝赋值，要么用移动移交所有权（Rule of 5）。否则默认拷贝会制造"两个对象指向同一资源"的重复释放。

  3. 填空：让一个 ByteStream 只能有一个主人，要 ______ 拷贝、提供 ______。

  4. 简答：哪些"退出"会绕过析构？嵌入式怎么补救？

    硬件异常（HardFault 等）、longjmp/直接改 PC、复位都会绕过析构。补救靠第①册 Module 08 的机制：看门狗、复位原因、备份寄存器、上电自检——而不是靠 RAII。

  5. 判断：RAII 一定会带来运行时开销（比如虚函数/堆分配）吗？

    不一定。像 GpioPin 这种无虚函数、栈上构造的类，构造/析构就是几条内联指令，运行时开销≈0。开销来自你选择实现 RAII 的方式（是否用虚函数、是否动态分配），不是 RAII 本身。

Module 03 · 编译期计算

constexpr 与编译期计算

C 里生成一张查找表，要么手抄、要么写脚本生成、要么运行时初始化。C++ 把它们统一成一件事： 让计算发生在编译期，Flash 里只留结果表。这一节讲 constexpr/consteval/constinit， 以及它们带来的真实账单。

◷ 约 60 分钟◈ CRC 查表编译期生成⚑ 零运行时开销的典范

3.1 把计算搬到 Flash 里

嵌入式最经典的一类优化是"空间换时间"：CRC、三角、对数、Gamma 校正……都预先算成一张表，运行时只查表。 C 的问题在于"表从哪来"：手抄容易错、脚本生成要额外工具、运行时初始化又要占启动时间与 RAM。

3.2 一个 consteval 的 CRC8 表

constexpr 是"可以在编译期求值"；consteval（C++20）更强：必须在编译期求值，否则直接编译失败。 编译期生成查找表用 consteval 最贴切 —— 它保证这张表绝不会在运行时被重新计算。

crc_table.cpp — 表在编译期生成，运行时只查表 C++ 
// crc_table.cpp —— 同一份"算法"，编译期跑一遍生成表
#include <cstdint>
#include <array>

// consteval：保证这张表只能在编译期算出来（写错成运行时一律编译失败）
consteval std::array<uint8_t, 256> make_crc8_table() {
    std::array<uint8_t, 256> t{};
    for (int i = 0; i < 256; i++) {
        uint8_t c = (uint8_t)i;
        for (int b = 0; b < 8; b++)
            c = (uint8_t)((c << 1) ^ ((c >> 7) ? 0x07 : 0));
        t[i] = c;
    }
    return t;
}

// 表落进 .rodata（Flash），不占 RAM、不需要运行时初始化
inline constexpr auto CRC8_TABLE = make_crc8_table();

uint8_t crc8(const uint8_t* d, uint32_t n) {
    uint8_t c = 0;
    while (n--) c = CRC8_TABLE[c ^ *d++];
    return c;
}
crc_bit.cpp — 对照：不查表、逐位算 C++ 
// crc_bit.cpp —— 不建表，每个字节多算 8 次位运算
#include <cstdint>

uint8_t crc8_bitwise(const uint8_t* d, uint32_t n) {
    uint8_t c = 0;
    while (n--) {
        c ^= *d++;
        for (int i = 0; i < 8; i++)
            c = (uint8_t)((c << 1) ^ ((c >> 7) ? 0x07 : 0));
    }
    return c;
}
crc_runtime.cpp — 对照二：C 的老路子，表放 RAM、启动时算一遍 C++ 
// crc_runtime.cpp —— 同一份算法，但表放在 RAM，等启动时填
#include <cstdint>

static uint8_t s_table[256];   // .bss：256 字节 RAM，等 crc8_init() 来填

void crc8_init() {             // 启动流程里调用一次
    for (int i = 0; i < 256; i++) {
        uint8_t c = (uint8_t)i;
        for (int b = 0; b < 8; b++)
            c = (uint8_t)((c << 1) ^ ((c >> 7) ? 0x07 : 0));
        s_table[i] = c;
    }
}

uint8_t crc8_rt(const uint8_t* d, uint32_t n) {
    uint8_t c = 0;
    while (n--) c = s_table[c ^ *d++];
    return c;
}
✔ 本机实测账单（-Os -std=c++20，.o text 字节）

查表版 = 288 字节（其中表本身 .rodata.CRC8_TABLE 占 0x100 = 256 字节）； 逐位版 = 48 字节。 也就是说：净增约 240 字节 Flash（288 − 48）换来"每字节只查一次表"，其中表本身 256 字节，而查表版代码比逐位版还少 16 字节 —— CRC 常在收包热路径上，这笔交易通常划算。 关键是：这 256 字节是编译期算好直接放进 Flash 的，不占 RAM、不占启动时间，源码里也没有那 256 个魔法常数。

作为对照，C 里最常见的"启动时建表"写法（下面第三个文件 crc_runtime.cpp）确实更省 Flash—— 但那 256 字节并没有消失，它只是从 Flash 挪进了 RAM 的 .bss，另外还要搭上一段启动代码。 三种写法的账单见 FIG 3.1 与下面的实测。

⚠ "启动时建表"还藏着一个正确性陷阱

crc8_rt() 依赖 s_table；若 crc8_init() 没被调用（或调用次序不对）， .bss 初值全 0，查表会静默返回错误的 CRC —— 不崩、不报错，最难查。 走这条路务必：① 在启动流程里明确、且先于任何使用地调用 crc8_init()； ② 用一个"是否已初始化"的标志/断言兜底；③ 双核（如 ESP32）或中断里并发调用时 s_table 会被撕裂，需临界区或改用编译期表。 而这正是 consteval 一次性消除的问题：表在 Flash 里、天生只读、无需初始化。

3.3 constexpr 寄存器视图 + static_assert

第①册用 offsetof + _Static_assert 把寄存器偏移钉进编译期。C++ 里这套照旧，而且 constexpr 还能把"位域描述"也变成编译期常量，供 static_assert 校验。

regs.hpp — 寄存器偏移与位域，全在编译期校验 C++ 
// regs.hpp —— constexpr 描述 + static_assert 把手册钉进代码
#include <cstdint>
#include <cstddef>

struct gpio_regs {
    volatile uint32_t crl;    // 0x00
    volatile uint32_t crh;    // 0x04
    volatile uint32_t idr;    // 0x08
    volatile uint32_t odr;    // 0x0C
    volatile uint32_t bsrr;   // 0x10
};

// 编译期断言：布局一旦被改动，这里立刻报错（不用等运行期）
static_assert(offsetof(gpio_regs, odr)  == 0x0Cu, "ODR 偏移应为 0x0C");
static_assert(offsetof(gpio_regs, bsrr) == 0x10u, "BSRR 偏移应为 0x10");

// constexpr：把"位号/宽度"写成编译期常量，运行时零成本
struct Field { uint8_t pos; uint8_t width; };
constexpr Field CRL_MODE0{0, 2};        // CRL 里每个引脚低 2 位是 MODE
constexpr Field CRL_CNF0 {2, 2};        // 高 2 位是 CNF
constexpr uint32_t field_mask(Field f) { return ((1u << f.width) - 1u) << f.pos; }
static_assert(field_mask(CRL_MODE0) == 0x3u, "MODE 掩码应为 0x3");
static_assert(field_mask(CRL_CNF0)  == 0xCu, "CNF 掩码应为 0xC");

// constinit（C++20）：要求"常量初始化"，从根本上消除跨 TU 的动态初始化顺序问题
constinit uint32_t g_error_count = 0;
◆ constexpr / consteval / constinit 一句话区分
  • constexpr：可以在编译期求值（也可在运行期）——"能省则省"。
  • consteval：必须在编译期求值——用它来强制"这张表/这个常量绝不可能是运行期算的"。
  • constinit：要求变量做常量初始化（constant initialization，在 main 前由编译器/加载器完成）。它与"动态初始化"互斥，因此根本不存在跨 TU 的动态初始化顺序问题（SIOF）。它不代表不可改——可以配合可变变量。
⚠ 为什么需要 constinit：一个 SIOF 反例

两个 TU 各有一个全局对象，构造顺序由链接器决定、标准不保证： a.cpp 里 extern int g_limit; 的构造函数读 g_limit， 而 b.cpp 里 int g_limit = 100; —— 若 a 的构造函数先跑，就读到 0。 把 g_limit 写成 constinit int g_limit = 100;，它就被强制常量初始化、在任何动态构造之前就绪，问题消失。
边界：constinit 要求初始化器本身是常量表达式（类类型需要 constexpr 构造）；它不适用于函数局部静态，也不改变可写性。

✔ 两个容易忽略的细节：inline 与"实体化"
  • 为什么写 inline constexpr auto CRC8_TABLE：constexpr 的命名空间作用域变量默认有内部链接，每个包含它的 TU 都会各存一份；加 inline（C++17）后它是唯一实体，多个 TU 共享同一份、不重复占 Flash。
  • constexpr ≠ 不进存储：只要表被运行期代码引用（哪怕只取地址），编译器就必须为它开出实体（本例就是 .rodata 里的 256 字节）；只有"纯在常量表达式里用、从不被运行期触碰"的 constexpr 变量才可能完全不进镜像。
  • 为什么用 std::array 而不是 C 数组：std::array 可被 constexpr 函数按值返回、能整体拷贝/比较，且 ABI 上与 C 数组完全等价（零额外开销）；原始指针不行，std::span 是运行期视图、不能用于常量表达式返回。

Module 04 · 零开销抽象

模板与零开销抽象

第①册用"虚表 + void* ctx"实现多态，每对象多一个指针、每调用一次间接跳转。 C++ 还提供了另一条路：把分派挪到编译期——策略模板、CRTP、if constexpr。 两条路都要会用，关键是知道各自什么时候划算。

4.2 策略模板：把"后端"变成模板参数

同一个 UART 的发送路径，可能有"阻塞写"和"DMA 写"两种后端。虚表版本要在每个对象里存一个 ops 指针、每次发送一次间接跳转； 策略模板把后端当作模板参数，调用被编译成立即数的静态调用，编译器还能顺手内联。

uart_policy.cpp — 后端在编译期确定，零间接跳转 C++ 
// uart_policy.cpp —— 两种后端，同一套上层代码（STM32F1 USART：SR@0x00, DR@0x04）
#include <cstdint>

struct BlockingBackend {
    static void send(volatile uint32_t* reg, uint8_t b) noexcept {
        while (!(reg[0] & 0x80u)) { }        // 等 SR 的 TXE（bit7）
        reg[1] = b;                          // 写 DR
    }
};
struct DmaBackend {
    static void send(volatile uint32_t* reg, uint8_t b) noexcept {
        reg[3] = (uint32_t)b;                // 示意：把数据/搬运交给 DMA 通道
    }
};

// 策略模板：Backend 是"编译期参数"
template <class Backend>
class Uart {
public:
    explicit Uart(volatile uint32_t* reg) noexcept : reg_(reg) {}
    void write_byte(uint8_t b) noexcept { Backend::send(reg_, b); }
private:
    volatile uint32_t* reg_;
};

void use_blocking(volatile uint32_t* r) { Uart<BlockingBackend> bus(r); bus.write_byte(0x10); }
void use_dma(volatile uint32_t* r)      { Uart<DmaBackend>      bus(r); bus.write_byte(0x10); }
◆ 代价对比

虚表版：对象多 4 字节 vptr；调用是一次间接跳转；好处是可以在运行期换后端。 策略模板版：对象不含 vptr；调用是静态调用、可内联；代价是"后端必须在编译期确定"， 且每换一个后端就生成一份 Uart<Backend> 的代码（实例化膨胀，见 §4.5；那里的探针用一个同构的 Spi<Policy> 薄例子来量字节）。 选哪个取决于"后端要不要运行期切换"——要，用虚表；不要，用模板。

4.3 CRTP：让基类"看见"派生类

有时你想要继承的复用、又不想付 vptr 的代价。CRTP（Curiously Recurring Template Pattern）让基类把派生类当作模板参数， 从而在编译期完成"调用派生类实现"这件事：

crtp.cpp — 静态多态：无 vptr 的"继承 + 覆写" C++ 
// crtp.cpp —— 基类通过模板参数知道派生类，调用在编译期解析
#include <cstdint>

template <class Derived>
struct SensorBase {
    uint16_t read() noexcept {
        return static_cast<Derived*>(this)->read_raw();   // 编译期绑定到 Derived::read_raw
    }
};

struct TempSensor : SensorBase<TempSensor> {
    uint16_t read_raw() noexcept { return 2500; }          // 25.00℃ * 100
};
struct HumidSensor : SensorBase<HumidSensor> {
    uint16_t read_raw() noexcept { return 4800; }
};

template <class S>
uint16_t sample(S& s) noexcept { return s.read(); }        // 可为任意 SensorBase 派生类生成一份
⚠ CRTP 的代价与陷阱
  • 无 vptr、调用可内联 —— 但每个派生类型都生成一份基类代码（和策略模板一样会膨胀）。
  • 它不是"运行期多态"：无法用基类指针统一存放不同派生对象。需要"一批异构对象"时，还是得回到虚表。
  • 写法略绕（static_cast<Derived*>(this)），团队要约定统一，否则可读性下降。

4.4 if constexpr：只编译需要的那条分支

以前用 #if/模板特化做"按类型走不同实现"，现在用 if constexpr 更直观： 条件为假的分支根本不会被实例化（不是"运行期不走"，而是"编译期不生成"）。 但别误解成"整块跳过"：被丢弃分支里的非依赖名（不依赖模板参数的名称）仍要经过语法与名称检查，写错照样编译不过；真正被丢弃的是依赖模板参数的那部分实例化。

if_constexpr.cpp — 编译期分支，未选中的分支不生成 C++ 
// if_constexpr.cpp —— 按元素宽度选择不同的长度计算
#include <cstdint>

template <class T>
uint32_t byte_count(const T* /*p*/, uint32_t n) noexcept {
    if constexpr (sizeof(T) == 1) {
        return n;                 // uint8_t：个数就是字节数
    } else {
        return n * (uint32_t)sizeof(T);
    }
}

uint32_t f8(const uint8_t* p, uint32_t n) { return byte_count(p, n); }
uint32_t f32(const uint32_t* p, uint32_t n){ return byte_count(p, n); }
dispatch_traits.cpp — if constexpr + 类型特征：按"有无符号"选实现 C++ 
// dispatch_traits.cpp —— 编译期按类型特征分派，未选分支不生成
#include <cstdint>
#include <type_traits>

template <class T>
constexpr bool fits_u16(T x) noexcept {
    if constexpr (std::is_unsigned_v<T>) {
        return x <= 0xFFFFu;                                  // 无符号：只查上界
    } else {
        return x >= 0 && static_cast<uint32_t>(x) <= 0xFFFFu;  // 有符号：还要查下界
    }
}

static_assert(fits_u16(1000u), "uint 1000 放得下");
static_assert(!fits_u16(-1),   "负数放不进 u16");

int encode(uint32_t v) noexcept { return fits_u16(v) ? 1 : 0; }

4.5 代价：模板实例化膨胀

✔ 一句话原则

模板适合"薄而通用"的代码（策略、类型安全包装、编译期计算）， 不适合把大块逻辑塞进模板头文件——那会让每份实例化都拖着整块代码。体积敏感时，用 -ffunction-sections 加 --gc-sections 兜底。

✔ 控制膨胀的另外两件工具
  • -flto（链接期优化）：让"跨 TU 内联 + 删死代码"在链接期统一发生，常能显著压掉被多处实例化又高度重复的模板代码；代价是编译/链接变慢，且需工具链带 LTO 插件（Arm GNU Toolchain 支持）。
  • 显式实例化 + extern template：在某个 .cpp 里写 template class Spi<Blocking>; 只生成这一份；在头文件里写 extern template class Spi<Blocking>; 让其它 TU 不再各生成一份。适合"实例化清单已知且有限"的场景。

4.6 进阶：用 extern template 控制"谁生成这份实例"

--gc-sections 删的是"没人引用的"实例；但"被引用了、却每个 TU 各生成一份"的重复，它管不了。 这种重复在对象文件层面是真实存在的（每个 TU 一份 weak 定义）。标准给了另一种控制手段：显式实例化 + extern template。

extern_template.cpp — 一个显式实例化点，其余 TU 不再生成 C++ 
// extern_template.cpp —— 模板被多个 TU 使用时的两种写法
#include <cstdint>

struct Blocking { static constexpr uint32_t spins = 3; };

template <class P>
struct Engine {
    __attribute__((noinline))
    static uint32_t run(uint32_t w) {
        for (uint32_t i = 0; i < P::spins; ++i) w = w * 1664525u + 1013904223u;
        return w;
    }
};

// ① 放在头文件里：告诉所有 TU"Engine<Blocking> 别在这里生成"
extern template struct Engine<Blocking>;

// ② 放在唯一的 .cpp 里：显式实例化，真正生成这一份
template struct Engine<Blocking>;

uint32_t use_engine(uint32_t w) { return Engine<Blocking>::run(w); }

5.1 所有权：unique_ptr 为什么是零开销的

std::unique_ptr<T, D> 就是"一个 T* 加一个删除器 D"。 当 D 是空类型（无状态）时，编译器用空基类优化把它压成 0 字节 —— 于是 unique_ptr<T> 的大小恰好等于一个指针，析构时静态调用删除器。

unique_handle.cpp — 自定义删除器 + 大小断言 C++ 
// unique_handle.cpp —— 用 unique_ptr 表达"独占所有权"
#include <memory>
#include <cstdint>

struct Session {
    int  id;
    void (*close)(int);
};

// 删除器：无状态 → 可被空基类优化，不占额外空间
struct SessionCloser {
    void operator()(Session* s) const noexcept {
        if (s && s->close) s->close(s->id);
    }
};
using SessionPtr = std::unique_ptr<Session, SessionCloser>;

// 关键：unique_ptr<T>（默认删除器）与裸指针同宽
static_assert(sizeof(std::unique_ptr<int>) == sizeof(int*), "unique_ptr 不该比裸指针大");

// 注意：删除器若"有状态"（比如存了一个上下文指针），它就会被算进去
struct CtxCloser { void* ctx; void operator()(Session*) const noexcept {} };
static_assert(sizeof(std::unique_ptr<Session, CtxCloser>) > sizeof(int*), "有状态删除器要占空间");

unique_ptr<T> = 一个指针：不引入运行时开销，却让"谁负责释放"变成类型事实。 它是 RAII（Module 02）在"句柄"上的标准应用。注意两点：① 删除器有状态就会占空间；② 它默认用 delete， 若对象不是 new 出来的（比如是静态内存里的对象），要换成"不 delete"的删除器。

✔ 删除器的几种形态与开销（32 位 ARM）
  • 无状态函数对象（如 SessionCloser）：被空基类优化，0 字节 → 整体 = 1 个指针（4 字节）。
  • 无捕获 lambda：同样是无状态类型，结果同上。
  • 函数指针 unique_ptr<T, void(*)(T*)>：删除器自身就是一个指针 → 整体 8 字节（本例 sz_cap）。
  • 有状态对象（存池指针 / 上下文）：多存一分状态；成员若可用 [[no_unique_address]]（C++20）标出，空成员不占位。

5.2 placement new：在静态内存上"构造"对象

MCU 上我们常常手头有一块静态内存（全局数组 / 专用段 / 内存池），不想每次都动态分配。 placement new 让你"在这块内存上调用构造函数"。要澄清一个常见误解： placement new 本身并不是 RAII —— 它只做"显式构造"，析构也要显式调用； 想让它变成 RAII，得自己（或用 unique_ptr + 自定义删除器）包一层。

placement.cpp — 静态存储 + 显式构造/析构 C++ 
// placement.cpp —— 存储来自静态数组，构造/析构仍然是显式的一对
#include <new>          // placement new
#include <cstdint>

class Logger {
public:
    explicit Logger(uint32_t sink_addr) noexcept : sink_(sink_addr) {}
    void put(char c) noexcept { (void)c; /* 写 sink_ */ }
    ~Logger() noexcept { /* 关闭、flush 等 */ }
private:
    uint32_t sink_;
};

// 存储：静态、对齐满足 Logger 的要求
alignas(Logger) static uint8_t g_logger_mem[sizeof(Logger)];

// 返回指针：由调用方持有，并在适当时机显式析构
Logger* bring_up_logger(uint32_t addr)
{
    Logger* lg = new (g_logger_mem) Logger(addr);   // 在静态内存上构造
    lg->put('A');
    return lg;               // 调用方在适当时机 lg->~Logger()
    // ⚠ 在 lg->~Logger() 之前再次调用本函数 → 把新对象构造到仍存活的对象上（UB）
}
⚠ placement new 的三条纪律
  • 对齐：存储必须满足类型的对齐要求，用 alignas(T) 明确写出来。
  • 不配对的析构 = 资源泄漏：placement new 出来的对象，析构要自己调（p->~T()）—— 它不在栈上，没有自动析构。
  • 别和 delete 混用：不能用 delete p 释放 placement 对象（那会走堆），要用 RAII 包装或显式析构。
  • 同一块存储上，前一个对象必须先析构、再构造下一个：在旧对象仍存活时就地 placement new 一个新对象，是未定义行为（旧对象没被销毁）。

5.3 std::span：把"指针 + 长度"变成一个类型

第①册里到处都是 (const uint8_t* buf, uint32_t len) 这样的成对参数 —— 忘了传长度、或长度传错是常见 bug。 std::span（C++20）把两者绑成一个视图对象（不拥有数据），接口与调用都更安全。

span.cpp — 视图：不拷贝、不拥有、自带长度 C++ 
// span.cpp —— 用 std::span 传"一段只读字节"
#include <span>
#include <cstdint>
#include <array>

// 收方：不关心来源，只在视图上操作
uint8_t checksum(std::span<const uint8_t> data) noexcept {
    uint8_t s = 0;
    for (uint8_t b : data) s = (uint8_t)(s + b);
    return s;
}

void demo() noexcept {
    std::array<uint8_t, 4> a{1, 2, 3, 4};
    uint8_t raw[3] = {9, 8, 7};

    (void)checksum(a);              // 从 std::array 构造视图
    (void)checksum(raw);            // 从 C 数组构造视图（长度自动推出）
    (void)checksum({raw, 2});       // 显式取前 2 个：`span(ptr, len)` 的老写法也有了类型
}
✔ 为什么它值得用

std::span 是非拥有视图（两个机器字：指针 + 长度），零拷贝、零分配。 它把"指针 + 长度"从"两个要记得配对传的参数"变成"一个不可能对不上的对象"—— 这正是第①册 Module 03 想表达的"类型即护栏"。 注意它不是所有者的替代品：它不负责释放，别拿它当 unique_ptr 用。

// fixed_pool.cpp —— 把"固定块池"和"所有权"接起来
#include <memory>
#include <array>
#include <cstdint>

struct Msg { uint8_t data[32]; bool in_use; };

class MsgPool {
public:
    Msg* acquire() noexcept {
        // 直观版：线性找一个空块（最坏 O(n)）。要真正的 O(1)，改成空闲链表 —— 见下方探针 pool_alloc.cpp
        for (auto& m : pool_) if (!m.in_use) { m.in_use = true; return &m; }
        return nullptr;                 // 池满：是要处理的设计情况，不是"分配失败"
    }
    void release(Msg* m) noexcept { if (m) m->in_use = false; }
private:
    std::array<Msg, 8> pool_{};          // 全部静态存储，零碎片
};

// 有状态的删除器：它知道归还到哪个池（所以比空删除器多占一个指针，§5.1）
struct PoolDeleter {
    MsgPool* pool;
    void operator()(Msg* m) const noexcept { if (pool) pool->release(m); }
};
using MsgHandle = std::unique_ptr<Msg, PoolDeleter>;

MsgHandle acquire_msg(MsgPool& p) noexcept {
    return MsgHandle{ p.acquire(), PoolDeleter{&p} };   // 离开作用域自动 release
}

void use(MsgPool& pool) {
    MsgHandle h = acquire_msg(pool);
    if (!h) return;                       // 池满
    h->data[0] = 0xAA;
    // 作用域结束 → ~unique_ptr → PoolDeleter → pool.release(h)
}

✕ M0 上的坑：原子读-改-写"编得过、链不过"

Cortex-M0/M0+ 没有 LDREX/STREX。所以 std::atomic<uint32_t> 的 fetch_add/compare_exchange 这类读-改-写操作，编译器会生成对 __atomic_fetch_add_4 等外部函数的调用 —— 它们要么由 libatomic 提供，要么链不过。 而且 libatomic 在 M0 上的实现本质是加锁回退（不是免等待），即使链上了，放进 ISR 也可能破坏实时性、引发优先级反转。 这与第①册 §6.8 的结论一致：M0 上要么改用"关中断临界区"，要么软件实现原子序列，别指望 lock-free 的 std::atomic。 注意：单纯的 load/store 仍是单条指令，没问题；出问题的是"读-改-写"。

6.3 六种 memory_order 与屏障的对应

memory_order 描述的是"这次原子操作与它周围访问的相对顺序"，不是"指令执行顺序"。 在 Cortex-M 上，它们大体映射到 DMB/DSB 或干脆不需要屏障：

memory_order语义Cortex-M 上的典型产物
relaxed只保证原子性，不约束顺序不加屏障（M3 上是 ldrex/strex；M0 走 __atomic_*）
acquire（读）其后的读写不能上移到它前面ld + dmb ish（读侧屏障）
release（写）其前的读写不能下移到它后面dmb ish + str（写侧屏障）
acq_rel读-改-写同时具有两者语义两侧屏障
seq_cst额外要求全局单一全序（最强）通常 dmb ish；单核上往往与 acq_rel 差异很小
consume依赖顺序（实践上多被当作 acquire）标准不建议用，按 acquire 处理
◆ 编译屏障 vs 硬件屏障
  • std::atomic_signal_fence：只约束编译器（不生成 DMB），等价于 asm volatile("" ::: "memory")。用于"同一内核里、编译器别重排"。
  • std::atomic_thread_fence：生成硬件屏障（如 DMB），跨执行单元可见性用它。
  • 对应第①册的：编译屏障 asm volatile("" ::: "memory") / 硬件屏障 __DMB()/__DSB()。
⚠ 三条屏障别混用：DMB / DSB / ISB

memory_order 只映射到 DMB；另外两条不是"内存序"语义，而是"等完成"与"重新取指"，要你在改系统寄存器、进 WFI 前手动插入：

指令管什么典型场景
DMB数据内存屏障：屏障前的内存访问，对"屏障之后发生的访问"可见release/acquire、共享数据与标志的顺序
DSB数据同步屏障：比 DMB 更强，要等到屏障前的所有内存访问真正完成才继续进 WFI / 复位前、切换栈、改 SCB 前确保写入落地
ISB指令同步屏障：清空流水线，让其后指令重新取指写 VTOR/NVIC/系统控制寄存器之后、开关中断之后

一句话记法：DMB 管顺序、DSB 等完成、ISB 重取指。只做共享数据同步时，通常只有 DMB 出现。

⚠ 反例：为什么 relaxed 不够（一个能复现的错序）

生产者先把结果写进 g_data，再用标志通知消费者。若标志用 relaxed， 编译器/处理器可以把"写数据"挪到"写标志"之后 —— 消费者就会看到"标志已置位、数据还是旧的"。 这不是理论：换优化等级或换个核，就可能复现。

relaxed_bad.cpp — relaxed 标志允许"看到标志却看不到数据" C++ 
// relaxed_bad.cpp —— 用 relaxed 标志：错序是允许的
#include <atomic>
#include <cstdint>

static uint32_t g_data = 0;
static std::atomic<uint32_t> g_flag{0};

void producer() {
    g_data = 42;
    // ✕ relaxed：不约束顺序，写 g_data 可能被挪到写标志之后
    g_flag.store(1, std::memory_order_relaxed);
    // ✔ 正解：g_flag.store(1, std::memory_order_release);
}

bool consumer(uint32_t* out) {
    if (g_flag.load(std::memory_order_relaxed) == 1) {   // ✔ 正解：load(std::memory_order_acquire)
        *out = g_data;                                    // relaxed 下，这里可能是旧值
        return true;
    }
    return false;
}

⚠ 另一种互斥：自旋锁（atomic_flag），但别在 ISR 里用

std::atomic_flag 是标准保证免锁的原子布尔，用它可写一个自旋锁 —— 也是"把 volatile 换成 atomic"之外， 处理"短临界区"的一种正规写法：

spinlock.cpp — atomic_flag 自旋锁（acquire/release） C++ 
// spinlock.cpp —— 用 atomic_flag 实现自旋锁（acquire/release 语义）
#include <atomic>
#include <cstdint>

class SpinLock {
public:
    void lock() noexcept {
        while (flag_.test_and_set(std::memory_order_acquire)) { /* 自旋等待 */ }
    }
    void unlock() noexcept {
        flag_.clear(std::memory_order_release);
    }
private:
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
};

static SpinLock g_lock;
static uint32_t g_counter = 0;

void locked_inc() {
    g_lock.lock();
    g_counter++;              // 临界区：只在这里改
    g_lock.unlock();
}

M3 上它编译成 ldrexb/strexb + 两道 dmb（实测见探针第 6 节）； 但 M0 上没有独占访问指令，会退化成库调用（不再是纯 inline）。更要记住两条纪律： ① 绝不在 ISR 里取自旋锁 —— 若被打断的代码正持有它，中断会永远自旋（死锁）； ② 自旋空烧周期与电量，长临界区应改用"关中断"或调度器互斥量。它适合"极短、只在主循环上下文竞争"的临界区。

6.4 经典模式：ISR 与主循环共享的双缓冲

最常见的并发场景：中断填一块缓冲，主循环取走处理。用 release/acquire 把"数据写好"与"标志置位"的顺序钉死， 才能保证主循环看到标志时，数据一定已经写好。

double_buffer.cpp — release/acquire 保证"先数据后标志" C++ 
// double_buffer.cpp —— 两块缓冲各带一个"空闲/就绪"状态位
#include <atomic>
#include <cstdint>

struct Frame { uint8_t data[16]; };

static Frame g_buf[2];
static std::atomic<uint8_t> g_state[2];    // 0 = 空闲（生产者可写）；1 = 就绪（消费者可读）

// 中断侧（生产者）：找一块空闲缓冲 → 填数据 → release 标"就绪"
bool isr_fill(const uint8_t* src) {
    for (int i = 0; i < 2; i++) {
        if (g_state[i].load(std::memory_order_acquire) == 0) {
            for (int k = 0; k < 16; k++) g_buf[i].data[k] = src[k];
            g_state[i].store(1, std::memory_order_release);  // 数据先落地，再发布"就绪"
            return true;
        }
    }
    return false;   // 两块都还没被消费：丢弃本帧（工程上应计数而非静默丢）
}

// 主循环侧（消费者）：找到就绪缓冲 → 取数据 → release 标"空闲"归还
bool main_poll(Frame* out) {
    for (int i = 0; i < 2; i++) {
        if (g_state[i].load(std::memory_order_acquire) == 1) {
            *out = g_buf[i];                                 // 此刻 data 一定已写好
            g_state[i].store(0, std::memory_order_release);  // 归还：生产者以后可复用
            return true;
        }
    }
    return false;
}
SEQ 6.1 双缓冲状态位：ISR 填"空闲"块并发布"就绪"，主循环取走再归还（release ↔ acquire）
⚠ 三条纪律
  • 单核也别省"顺序"：同核硬件按程序序看到自己的写，硬件 DMB 未必是必需的；但编译器仍可能把"数据写"与"标志写"重排 —— release/acquire 是把顺序钉死的标准写法（退一步至少也要编译屏障）。
  • 别用一个标志就地覆盖：ISR 可能在主循环正拷 g_buf[idx] 时再次触发并改写同一块；主循环末尾清标志还可能抹掉刚到达的新帧。给每块配独立状态位、生产者只写"空闲"块，才不会互相踩。
  • M0 上小心读-改-写：若标志需要 fetch_*/exchange 等操作，M0 会走外部原子函数（可能链不过）。只用 load/store 就没这个问题。

✔ 一条实用判据

上 M0 之前，问自己一句："这个共享量是不是只做了单次 8/16/32 位 load/store？" 是 → std::atomic 没问题；否（要读-改-写）→ 用关中断临界区把操作包起来。 这比"赌 M0 也有 lock-free"要稳得多。

更好的是让编译器替你判定：static_assert(std::atomic<uint32_t>::is_always_lock_free); —— 目标不支持时当场编译不过，而不是等到运行期才发现走了加锁回退（这句在 M0 上会直接失败）。

✔ 还该知道的几件事
  • 比较交换：compare_exchange_weak/strong 是无锁读-改-写的通用原语；weak 允许"伪失败"（配 while 循环用），strong 不会伪失败。用于链表/栈时要留意 ABA 问题。
  • atomic_flag：最简单的原子布尔，test_and_set()/clear() 保证免锁，适合做自旋锁。注意静态初始化——全局 atomic/atomic_flag 要在任何使用前完成初始化（常量初始化或 atomic_init）。
  • 单核同核上，顺序往往只需编译屏障：ISR 与主循环在同一核、按程序序看到彼此之前的写，硬件 DMB 未必必需；关键是别让编译器重排。用 release/acquire（或 atomic_signal_fence）表达是标准且省心的写法。

  1. 判断：volatile 能替代 std::atomic 吗？

    不能。volatile 只保证"每次真读真写、不合并删除"，既不含原子性、也不含内存顺序；读-改-写仍会撕裂、仍可能重排。原子性与顺序要用 std::atomic。

  2. 简答：为什么 M0 上 std::atomic<uint32_t>::fetch_add 可能链接失败？

7.1 enum class：有作用域、不隐式转 int

C 的 enum 会隐式转成 int，名字还泄漏到外层作用域。 enum class 同时解决这两点：名字带作用域、不隐式转换，而且可以指定底层类型以控制大小。

strong_enum.cpp — 编译器帮你拦住"混着用" C++ 
// strong_enum.cpp —— enum class 的作用域与强类型
#include <cstdint>

enum class State : uint8_t { Idle, Run, Fault };     // 明确 1 字节
enum class Err   : uint16_t { Ok = 0, Timeout = 1, Crc = 2 };

static_assert(sizeof(State) == 1, "State 应为一字节（省 RAM）");

void set_state(State s) noexcept { (void)s; }

void demo() noexcept {
    set_state(State::Run);        // ✔ 必须写全限定名
    // set_state(0);              // ✕ 编译错误：int 不能隐式转 State
    // if (State::Run == 0) {}    // ✕ 编译错误：不隐式转 int
    if (State::Run == State::Run) {}   // ✔ 同类型比较
    uint8_t raw = static_cast<uint8_t>(State::Fault);   // ✔ 要"落地"为整数得显式转
    (void)raw;
}
✔ 为什么值得

它把"State 与 Err 是两码事"从约定变成编译器强制： set_state(some_err) 直接编译失败。而底层类型可指定为 uint8_t，不存在"为了类型安全而变大"的问题。

⚠ enum class 默认不支持位运算

这是寄存器编程里最常踩的一条：enum class 不会隐式转成整数，所以 Irq::Rx | Irq::Tx、f & Mask 默认编译不过。 要当"标志位集合"用，就得自己提供 operator|/&/~：

irq_flags.cpp — 给 enum class 补上位运算 C++ 
// irq_flags.cpp —— enum class 当标志位用，必须自定义 operator
#include <cstdint>

enum class Irq : uint32_t {
    None = 0u, Rx = 1u << 0, Tx = 1u << 1, Err = 1u << 2
};

constexpr Irq operator|(Irq a, Irq b) noexcept {
    return static_cast<Irq>(static_cast<uint32_t>(a) | static_cast<uint32_t>(b));
}
constexpr bool has(Irq set, Irq bit) noexcept {
    return (static_cast<uint32_t>(set) & static_cast<uint32_t>(bit)) != 0u;
}

void enable(Irq) noexcept {}

void demo() noexcept {
    Irq f = Irq::Rx | Irq::Tx;        // ✔ 有了 operator| 才能组合
    enable(f);
    (void)has(f, Irq::Rx);            // ✔ 用辅助函数做"含某位"判断
    // 若没有上面的 operator|，`Irq::Rx | Irq::Tx` 这行会直接编译失败。
}

7.2 强类型单位：拦住"把毫秒传给微秒"

API 里成群的 uint32_t delay_ms/timeout_us 是 bug 温床：两者的类型都是 uint32_t， 传错不会报错，只会在运行期表现为"延时差 1000 倍"。用"标签 + 数值"的强类型可以彻底杜绝。

unit.cpp — 毫秒与微秒是两个类型（构造必须显式） C++ 
// unit.cpp —— 单位作为类型参数；编译期就能发现"传错单位"
#include <cstdint>

template <class Tag>
struct Unit {                          // 极简强类型：不同 Tag 就是不同类型
    uint32_t v;
    explicit constexpr Unit(uint32_t n) noexcept : v(n) {}   // 显式构造，杜绝 uint32_t 隐式进入
};

struct MsTag {}; struct UsTag {};
using Milliseconds = Unit<MsTag>;
using Microseconds = Unit<UsTag>;

constexpr Milliseconds ms(uint32_t n) noexcept { return Milliseconds{n}; }
constexpr Microseconds us(uint32_t n) noexcept { return Microseconds{n}; }

void delay(Milliseconds /*t*/) noexcept {}          // 只接受"毫秒"

void demo() noexcept {
    delay(ms(10));                 // ✔
    // delay(us(500));             // ✕ 编译错误：Microseconds 不是 Milliseconds
    // delay(10);                  // ✕ 编译错误：uint32_t 无法隐式转 Unit
}

◆ 强类型的正确姿势

不需要一上来就抄 std::chrono 那套（模板实例多、写法重）。嵌入式里更实用的是这种极简 Unit： 一个 tag 类型区分单位、一个 uint32_t 定宽度。零运行时开销（就是个包装）， 但把整类单位错误挡在了编译期。

✔ 但要清楚：强类型只解决"单位"，不解决"数值"
  • 换算与混算：ms + us、ms → us 默认不提供。要允许就自己写只接受同类型的 operator+，或显式给一个 to_us(ms) 换算函数 —— 别用隐式转换把它变回"能随便混"。
  • 溢出/饱和：Unit 里还是 uint32_t，相加照旧会按无符号回绕；实时语境下常要饱和而非回绕，得在 operator+ 里显式处理。
  • 别留可写裸成员：若把 v 暴露成到处可改的 public 成员，等于给护栏开了后门；尽早就地封装成只读访问（value()）或受限的算子。
unit_math.cpp — 只允许"同单位"运算，换算是显式函数 C++ 
// unit_math.cpp —— 强类型也要能"安全地算"：只提供同单位的 operator+
#include <cstdint>

template <class Tag>
struct Unit {
    uint32_t v;
    explicit constexpr Unit(uint32_t n) noexcept : v(n) {}
};

struct MsTag {}; struct UsTag {};
using Milliseconds = Unit<MsTag>;
using Microseconds = Unit<UsTag>;

// 只接受"同单位"相加：不同单位传进来直接编译失败
constexpr Milliseconds operator+(Milliseconds a, Milliseconds b) noexcept {
    return Milliseconds{a.v + b.v};          // 注意：仍会无符号回绕，实时场合要改成饱和
}
// 换算是显式的：调用方一眼看得见"这里在改单位"
constexpr Microseconds to_us(Milliseconds t) noexcept {
    return Microseconds{t.v * 1000u};        // 溢出由调用方负责（或加饱和检查）
}

void demo() noexcept {
    Milliseconds t = Milliseconds{5} + Milliseconds{10};   // ✔ 同单位
    Microseconds u = to_us(t);                             // ✔ 显式换算
    (void)u;
    // Milliseconds bad = Milliseconds{1} + Microseconds{2};   // ✕ 无匹配 operator+，编译失败
}

7.3 std::byte：字节就是字节

C 里"一字节"常用 uint8_t 或 char，两者都会隐式参与算术（加减乘）， 而字节通常不该做算术。C++17 的 std::byte 把"原始字节"与"数值"区分开：

byte_use.cpp — std::byte 只做位运算，不做数值运算 C++ 
// byte_use.cpp —— 原始字节用 std::byte；要算术先显式转
#include <cstddef>
#include <cstdint>

void fill(std::byte* p, std::size_t n, std::byte v) noexcept {
    while (n--) *p++ = v;
}

void demo(std::byte* buf) noexcept {
    fill(buf, 16, std::byte{0xAA});                 // 用花括号初始化，避免隐式整数
    std::byte b = buf[0];
    b = b | std::byte{0x01};                        // 位运算：允许
    // int x = b;                                   // ✕ 不隐式转整数
    uint8_t raw = std::to_integer<uint8_t>(b);      // ✔ 要当数值用时显式转
    (void)raw;
}

7.4 把寄存器布局钉进编译期（对照第①册）

第①册用 offsetof + _Static_assert 校验寄存器结构体。C++ 里除了沿用 offsetof，还能用 static_assert 把"位宽/位号/掩码"一起钉住，并配合强类型让"写错寄存器"也难以发生。

⚠ offsetof 有个前提：类型必须是"标准布局"

offsetof 只对标准布局类型（standard-layout）获得标准保证。一旦给寄存器视图加上构造函数、成员函数或访问控制（private/公私混排），它就不再是标准布局， offsetof 变成"有条件支持"（GCC 会报 -Winvalid-offsetof），断言随之失去意义。 所以寄存器视图要保持"纯数据成员 + 标准布局"，并把这个前提也一起断言出来：

// reg_field.cpp —— 位域描述是编译期常量，读改写是运行期几条指令
#include <cstdint>

struct Field { uint8_t pos; uint8_t width; };

constexpr uint32_t mask_of(Field f) noexcept { return ((1u << f.width) - 1u) << f.pos; }
constexpr uint32_t pack(Field f, uint32_t val) noexcept { return (val << f.pos) & mask_of(f); }
constexpr uint32_t unpack(Field f, uint32_t reg) noexcept { return (reg & mask_of(f)) >> f.pos; }

constexpr Field MODE0{0, 2};                 // 某寄存器第 0 号字段，2 位
static_assert(mask_of(MODE0) == 0x3u, "MODE0 掩码应为 0x3");

// 清字段再置值（读-改-写；并发/中断场景要配临界区，见 Module 06/08）
void set_field(volatile uint32_t* reg, Field f, uint32_t val) noexcept {
    *reg = (*reg & ~mask_of(f)) | pack(f, val);
}
uint32_t get_field(uint32_t reg, Field f) noexcept { return unpack(f, reg); }
⚠ 护栏也要"值得"

类型护栏的价值在于"拦住的错误确实可能发生"。给一个只在本文件内传一两次的短命值造一堆强类型，反而添乱。 经验法则：跨模块接口、容易混的单位/句柄、状态与错误码——这些地方加类型，收益最大。

✔ 与 std::chrono 的关系，以及 std::bit_cast
  • std::chrono 是标准库的强类型时间：std::chrono::milliseconds/microseconds 是不同类型，且自带换算（duration_cast、字面量 10ms）。但它模板实例多、写法重；MCU 上若只需"防串用"，本节的极简 Unit 更省事，要完整时间算术再上 chrono。
  • std::bit_cast（C++20）：在同大小、可平凡拷贝的类型间按位重解释（如把 uint32_t 的位模式转成 float），替代 union 双关或 memcpy：无 UB、可用于 constexpr。是"原始字节/寄存器值"场景的正规写法。
  • 别名与对齐：用 std::byte/unsigned char 访问任意对象是标准允许的；但用 uint32_t* 去解引用一个 std::byte 缓冲会违反严格别名与对齐 —— 这类"重解释"交给 bit_cast/memcpy，别硬转指针。

8.3 中断上下文里 volatile 与 atomic 的取舍

共享量用什么
ISR 只写、主循环只读的单字节/单字标志硬件层面单次对齐访问不会撕裂，所以 volatile 能工作；但按 C++ 内存模型，跨执行单元读写同一非 atomic 对象是数据竞争（UB） —— 规范做法用 std::atomic（配 relaxed 或 release/acquire）。这正是 M06 强调的"volatile ≠ atomic"
主循环/ISR 都要读-改-写的计数器M3+ 用 std::atomic；M0 用关中断临界区（Module 06）
多字节结构的一致性原子不够（多字节非原子）→ 临界区 + 双缓冲/release-acquire
✔ 让编译器替你判定"是否 lock-free"

把 std::atomic 放进 ISR 之前，先断言它是否免锁： static_assert(std::atomic<uint32_t>::is_always_lock_free);。 目标不支持时（例如 M0 上的读-改-写会走加锁回退）当场编译失败，好过等到运行期才发现。 边界：这条断言针对"读-改-写"类操作；单次 load/store 即便非 lock-free 也通常是普通访存。

8.4 用 C++ 写一个安全的 ISR 回调注册

第①册用"函数指针数组 + weak 默认实现"接管中断。C++ 里可以用编译期大小的表 + 类型化的注册做得更规整。 extern "C" 保证分发入口对 C/汇编可见（Module 09 细讲）。

isr_dispatch.cpp — 编译期定表 + 运行期注册 C++ 
// isr_dispatch.cpp —— 中断回调注册与分发
// 向量表项签名固定是 void(void)：IRQ 号从 IPSR 里取，不能当函数参数传进来
#include <cstdint>
#include <atomic>

using IsrHandler = void (*)(void* ctx);
struct Slot { IsrHandler fn; void* ctx; };      // 注册后不再改动 → 可安全发布

constexpr uint32_t kIrqCount = 8;
static_assert(kIrqCount > 0, "IRQ 表不能为空");

// 表项发布的是"指向不可变 Slot 的指针"：读侧一次原子 load 就得到一致快照
static std::atomic<const Slot*> g_slots[kIrqCount] = {};

// 注册：在主循环初始化阶段调用（此时对应 IRQ 还没使能）；发布用 release
bool isr_register(uint32_t irq, const Slot* s) noexcept {
    if (irq >= kIrqCount) return false;
    g_slots[irq].store(s, std::memory_order_release);
    return true;
}

// 取当前异常号（IPSR）；IRQn = 异常号 - 16
static inline uint32_t current_exception() noexcept {
    uint32_t ipsr;
    __asm volatile("mrs %0, ipsr" : "=r"(ipsr));
    return ipsr & 0x1FFu;
}

// 向量表里每个 IRQ 项都指向它；签名必须是 void(void)
extern "C" void irq_dispatch(void) noexcept {
    uint32_t e = current_exception();
    if (e < 16u) return;                 // 系统异常（SysTick 等）另有入口
    const uint32_t irq = e - 16u;
    if (irq >= kIrqCount) return;
    const Slot* s = g_slots[irq].load(std::memory_order_acquire);   // 一致快照
    if (s && s->fn) s->fn(s->ctx);
}

// 一个具体处理函数：只做"取数据 + 置标志"，不做重活
static void uart_rx_isr(void* ctx) noexcept {
    volatile uint32_t* sr = static_cast<volatile uint32_t*>(ctx);
    (void)sr;                           /* 读 SR、清标志、把字节塞进环形缓冲 */
}

◆ 这段代码为什么"安全"

三栏的划分标准只有一条：这件事在中断上下文里是否"可重入、无阻塞、无分配、时间有界"。 白名单里的每一项都不需要调用任何库函数，所以编译器能把它压成几条指令。 灰区不是"不能做"，而是"要用实测证明它在你的核上确实是一条指令"——下栏就是这项证明的样板： 同一份源码，M3 用硬件独占访问 ldrex/strex 完成读-改-写，没有任何未定义符号； M0+ 没有独占访问指令，编译器只能改成 bl __atomic_fetch_add_4， 于是你的中断里多了一次库函数调用，链接时还必须带上 libatomic。 同一句 C++，在 M0 上就不再是"白名单"了——这就是为什么 §8.3 说 M0 上读-改-写要用关中断临界区。

另一个几乎每个固件都要写的模式：中断写入、主循环读出的环形缓冲。用原子索引把"先写数据、再发布可读"钉住， 单生产者/单消费者（SPSC）下可以做到无锁、无分配、无阻塞 —— 中断侧只做几次整数运算和一次 release 发布。

ring_spsc.cpp — 中断只写、主循环只读的无锁环形缓冲 C++ 
// ring_spsc.cpp —— 单生产者（ISR）/ 单消费者（主循环）环形缓冲
#include <atomic>
#include <cstdint>
#include <cstddef>

constexpr std::size_t kCap = 64;                 // 实际可用 63：留一个空位区分"满/空"
static uint8_t g_buf[kCap];
static std::atomic<std::size_t> g_head{0};        // 生产者写
static std::atomic<std::size_t> g_tail{0};        // 消费者读

// 中断侧（生产者）：只写、无阻塞、无分配
bool ring_put(uint8_t b) noexcept {
    const std::size_t h   = g_head.load(std::memory_order_relaxed);
    const std::size_t nxt = (h + 1) % kCap;
    if (nxt == g_tail.load(std::memory_order_acquire)) return false;  // 满：丢弃并计数
    g_buf[h] = b;                                                     // 先写数据
    g_head.store(nxt, std::memory_order_release);                    // 再发布可读
    return true;
}

// 主循环侧（消费者）
bool ring_get(uint8_t* out) noexcept {
    const std::size_t t = g_tail.load(std::memory_order_relaxed);
    if (t == g_head.load(std::memory_order_acquire)) return false;    // 空
    *out = g_buf[t];                                                  // 此刻数据一定已写好
    g_tail.store((t + 1) % kCap, std::memory_order_release);
    return true;
}
✔ 为什么它是无锁且安全的

只有一个生产者改 g_head、一个消费者改 g_tail， 各自独占自己的索引，所以不需要互斥；生产者的 release 与消费者的 acquire 构成配对， 保证"读到新 head ⇒ 一定读得到对应数据"。留一个空位是把"满"与"空"区分开的经典技巧。 M0 上这套仍然成立 —— 因为用到的只有单次 load/store，没有读-改-写。

8.5 浮点与惰性保存（M4F/M7 注意）

带 FPU 的核（M4F/M7）在异常入口采用惰性保存：处理器总是会预留一段 FP 扩展帧的栈空间 （S0–S15 + FPSCR + 保留字），是否真正写回浮点寄存器由 FPCCR 的 ASPEN/LSPEN 控制 —— 只有异常处理里（或被打断的代码里）用到浮点时，才去写这些槽。 所以"没在中断里用浮点，栈还是变深了"正因为这段预留帧；而一旦中断里真的用了浮点， 还要多做实际的保存/恢复，栈峰值与进入/退出周期会进一步增加（第①册 Module 08 讲过这是"栈帧看着对不上"的常见原因之一）。

⚠ 三条建议
  • 中断里尽量不用浮点：能定点就定点；必须用时，评估它对最坏中断延迟与栈峰值的影响。
  • 给中断栈留足余量：FPU 扩展帧会让"一次中断吃多少栈"明显变大。
  • 统一浮点使用约定：团队约定"中断里禁用浮点"，比每个人各自判断更可靠。

  1. 判断：中断里可以 new 一个对象吗？

    不可以。new/delete/malloc 走堆，非重入且耗时不确定，会破坏中断的及时性甚至损坏堆状态。应改为预分配环形缓冲或内存池。

  2. 简答：为什么"中断里调用了一个带静态缓冲的函数"很危险？

    因为它是不可重入的：主循环正在用它时中断打断进来，又用同一个静态缓冲，就会互相覆盖。表现是"偶发数据错乱/卡死"，极难复现。中断里只能调可重入、无阻塞、无分配的函数。

  3. 填空：ISR 分发函数出口要写 ______，才能在向量表/汇编里用固定名字调用。

    extern "C"（关闭 C++ 名字修饰，保证符号名固定，Module 09 会细讲）。另外注意向量表项的签名固定是 void(void)：IRQ 号不能当函数参数传进来，要在处理函数里读 IPSR（如 mrs %0, ipsr）再算出 IRQn。

  4. 简答：为什么示例里要 Slot s = g_slots[irq]; 先拷贝一份再用？

    避免"读一半被改"造成 fn/ctx 错配：Slot（函数指针 + void*）在 32 位核上是 8 字节，普通拷贝会拆成两次访存，可能读到"新 fn + 旧 ctx"。所以改成发布"指向不可变 Slot 的指针"，读侧一次 atomic load(acquire) 拿到整块一致快照。也就是说：要一致，靠的是"原子地读一个指针"，而不是"拷贝一个多字节结构体"。

  5. 判断：带 FPU 的核在中断里用浮点没有额外代价。

    有额外代价。异常入口会触发浮点上下文（S0–S15/FPSCR）的惰性保存，增加栈用量与进入/退出周期。中断里应尽量用定点，或把浮点计算挪出中断。

  6. 找错：某 ISR 里写了 if (rx) { count++; buf[head++ % N] = dr; }，主循环也读 count。指出至少两处隐患。

    ① count++ 是读-改-写，若主循环也改就非原子、会丢更新（应按 M06 用 std::atomic 或临界区）；② head 与数据写入之间没有 release 约束，读者可能看到新 head 却读不到对应数据（应像 ring_spsc.cpp 那样先写数据、再 release 发布）；③ 对 count 的跨上下文裸访问还是数据竞争（UB）。

9.1 extern "C"：把名字修饰关掉

C++ 支持函数重载，所以编译器会把参数类型编码进符号名（名字修饰 / name mangling）。 例如 void uart_write(int) 在 C++ 里的符号可能是 _Z10uart_writei， 而在 C 里就是 uart_write。两边对不上，链接器就找不到符号。 extern "C" 告诉编译器："这个名字按 C 规则生成，不要修饰"。

crc_link.hpp — 一个可被 C 和 C++ 共用的头文件 C++ 
// crc_link.hpp —— 经典的"两面兼容"头文件写法
#ifndef CRC_LINK_HPP
#define CRC_LINK_HPP
#include <stdint.h>

#ifdef __cplusplus
extern "C" {
#endif

/* 这些函数对 C 和 C++ 都暴露同一个符号名 */
uint8_t crc8_link(const uint8_t* d, uint32_t n);
uint32_t version_link(void);

#ifdef __cplusplus
}
#endif
#endif /* CRC_LINK_HPP */
crc_link.cpp — 用 C++ 实现，但导出 C 符号 C++ 
// crc_link.cpp —— 实现可以是 C++（类、模板、constexpr 都在），出口是 C 符号
#include "crc_link.hpp"
#include <array>

namespace {
consteval std::array<uint8_t, 256> make_table() {
    std::array<uint8_t, 256> t{};
    for (int i = 0; i < 256; i++) {
        uint8_t c = (uint8_t)i;
        for (int b = 0; b < 8; b++) c = (uint8_t)((c << 1) ^ ((c >> 7) ? 0x07 : 0));
        t[i] = c;
    }
    return t;
}
constexpr auto TABLE = make_table();
}  // namespace

extern "C" uint8_t crc8_link(const uint8_t* d, uint32_t n) {
    uint8_t c = 0;
    while (n--) c = TABLE[c ^ *d++];
    return c;
}
extern "C" uint32_t version_link(void) { return 0x00010000u; }

◆ 记住三句话

9.2 结构体布局：什么时候能跨语言传

C 和 C++ 之间传结构体，前提是双方看到的内存布局完全一致。C++ 的"标准布局类型（standard-layout）"能满足这一点， 但一旦引入虚函数、多重继承、访问控制混排，布局就不再与 C 兼容。

类型特征能安全地跨 C/C++ 传吗
纯 POD（无虚函数、无访问控制、无基类）能（与 C 结构体布局一致）
含 private/public 混排成员标准布局性可能被破坏 → 不要跨语言传
含虚函数（有 vptr）不能（C 侧没有 vptr 的概念）
含基类通常不能；但"恰好含一个标准布局基类、且派生类无非静态数据成员"仍可能是标准布局 → 必须用 trait 具体断言，别凭经验
enum class（且指定 : uint8_t）能，但 C 侧必须用匹配的 uint8_t（C 的普通 enum 底层宽度是实现定义的 int，对不上）
⚠ "能跨语言传"的充分条件（不只是标准布局）

光"标准布局"还不够，两边还必须逐项一致：成员顺序与类型一致、位域宽度与顺序一致、 结构体对齐/pack一致（如 C 侧用了 #pragma pack）、bool 与 enum 的底层宽度一致。 只断言 sizeof 不够 —— 总大小相同、偏移却不同也能骗过你；要连 offsetof 一起断言（见下）。

abi_check.cpp — 用 trait 与断言把"可跨语言"钉死 C++ 
// abi_check.cpp —— 编译期确认"这个结构体能安全地给 C 用"
#include <cstdint>
#include <cstddef>
#include <type_traits>

struct Frame {              // 纯 POD，用于跨语言传递
    uint8_t  addr;
    uint8_t  len;
    uint16_t crc;
};

static_assert(std::is_standard_layout<Frame>::value, "必须标准布局才能给 C 用");
static_assert(std::is_trivially_copyable<Frame>::value, "必须可平凡拷贝");
static_assert(sizeof(Frame) == 4, "布局要与协议一致（本例 4 字节）");
// 只断 sizeof 不够：偏移也要钉住（总大小相同、偏移不同同样会错位）
static_assert(offsetof(Frame, addr) == 0, "addr 必须在偏移 0");
static_assert(offsetof(Frame, len)  == 1, "len  必须在偏移 1");
static_assert(offsetof(Frame, crc)  == 2, "crc  必须在偏移 2");

9.3 std::atomic 与 C11 _Atomic

C11 的 _Atomic 与 C++ 的 std::atomic 都表达"原子类型"，但它们的 ABI 不保证一致： 同一块共享内存被一边当 _Atomic int、另一边当 std::atomic<int> 访问，属于未定义行为。

⚠ 跨语言共享原子量的正确做法
  • 要么整块由一侧代码掌管（另一侧只通过函数访问，不直接读那个变量）。
  • 要么在边界处用明确的函数接口（extern "C" int counter_get(void)），把原子操作关在实现里。
  • 别指望"C 侧 _Atomic、C++ 侧 std::atomic 指向同一个变量"能正常工作。

9.4 混合链接：Makefile 要点

要点说明
分别用 gcc/g++ 编译.c 用 C 编译器、.cpp 用 C++ 编译器，各自带对应标准
用 g++ 链接链接阶段要拉入 C++ 运行库（libstdc++）；用 gcc 链可能报缺 C++ 符号（何时真的需要，见下）

⚠ "必须用 g++ 链接"要看情况

§9.1 的探针用 -nostdlib 链出 mixed.elf —— 那份代码没有全局构造、不用异常、不碰 libstdc++，所以 C 编译器也能链。 但只要用到 C++ 运行时设施（全局对象构造、异常、new、libstdc++ 组件），就必须用 g++ 链接（或显式补 -lstdc++ 与 __libc_init_array），否则报缺符号。

✔ 变量与链接性：不止函数
  • 命名空间作用域的变量同样不被名字修饰：C 侧可以直接链接 C++ 定义的全局变量（前提是类型/布局一致）。探针里的 g_calls 就是证据。
  • 但 const/constexpr 的命名空间作用域变量默认是内部链接（每个 TU 各一份），不能这样跨语言共享；要共享得显式写 extern，并保证只有一个定义。
  • 需要固定 C 名字的变量，用 extern "C" 修饰声明（如 extern "C" int g_flag;），保证裸名与单一实体。

  1. 简答：extern "C" 解决了什么问题？

    解决 C++ 名字修饰导致的符号名不一致：C 侧按 uart_write 找，C++ 却生成 _Z10uart_writei。加上它后符号名按 C 规则生成，两边能对上。它只影响链接名，不改变函数体。

  2. 判断：extern "C" 能修饰类的成员函数吗？

    成员函数不能（C 没有类概念）。对重载函数，准则是"同名最多只能有一个 extern "C" 版本"，其余重载仍走 C++ 链接。要跨语言暴露，通常在类外写一个 extern "C" 的自由函数作为门面。另注意：不同 TU 里写同名 extern "C" 会撞车，报重定义。

  3. 简答：什么结构体可以安全地跨 C/C++ 传递？

    标准布局 + 可平凡拷贝的（纯 POD）结构与 C 结构体布局一致，可以传。含虚函数（有 vptr）、基类、访问控制混排的类型布局与 C 不兼容，不能直接传。可用 is_standard_layout/is_trivially_copyable + static_assert 钉住。

  4. 判断：C 侧用 _Atomic int、C++ 侧用 std::atomic<int> 指向同一变量是安全的。

    不安全。两者 ABI 不保证一致，混用是未定义行为。正确做法是用函数接口把原子操作关在一侧，另一侧只通过函数访问。

  5. 填空：混合工程里，.c 用 ______ 编、.cpp 用 ______ 编，链接用 ______。

    arm-none-eabi-gcc / arm-none-eabi-g++ / 用 g++ 链接（保证拉入 C++ 运行库）。

  6. 诊断：a.cpp 与 b.cpp 各自在不同命名空间里定义了 extern "C" void foo(){}，单独编都过。一起链会怎样？

    报 foo is already defined（汇编/链接期）。因为 extern "C" 生成的是全局唯一的裸名，命名空间与重载都区分不了它，两个 TU 撞了同一个 C 符号。所以同名 extern "C" 只能有一处定义。

10.2 重构后：概念（concepts）+ 泛型驱动

用 C++20 的 concept，把"一个显示器"需要具备什么写成编译期约束： 上层函数模板收任何满足 Display 的类型，编译器在实例化时检查接口是否齐全 —— 不用虚表、不用 void*、不用手写 ops->。

display_after.cpp — 重构后：concept + 泛型，零 vptr C++ 
// display_after.cpp —— 用 concept 表达"什么是显示器"
#include <cstdint>
#include <concepts>

// 约束：任何满足它的类型都能当"显示器"用
template <class D>
concept Display = requires(D d, uint8_t on) {
    { d.init() } -> std::same_as<void>;
    { d.clear(on) } -> std::same_as<void>;
    { d.width() } -> std::convertible_to<uint16_t>;   // 只读查询
};

// 上层：对任意 Display 生成一份代码，调用在编译期解析、可内联
template <Display D>
void display_bring_up(D& d) {
    d.init();
    d.clear(1);
    (void)d.width();
}

// 一个具体实现：普通类，无虚函数、无 vptr
class St7789 {
public:
    explicit St7789(uint16_t w) noexcept : w_(w) {}
    void     init() noexcept         {}
    void     clear(uint8_t) noexcept {}
    uint16_t width() const noexcept  { return w_; }
private:
    uint16_t w_;
};

// 编译期就验证：St7789 满足 Display
static_assert(Display<St7789>);

void use() {
    St7789 lcd(320);
    display_bring_up(lcd);        // 无间接跳转、无 void* 强转
}

10.3 那还要不要虚表？—— 两个都要会

concept 方案很漂亮，但它丢失了运行期多态：St7789/Ili9341 是不同的类型， 没法放进"一个 Display* 数组"里在运行期遍历。所以真实工程里两者常并存：

需求用哪个
实现编译期已知、追求零开销与强检查concept / 模板
运行期要在一批"同接口不同实现"间切换/遍历虚表（或第①册的 ops 表）
边界清晰的两层：上层泛型、边界处擦除类型混合：内部用 concept，暴露给外部的接口用手写的函数指针表（或虚表）做一次类型擦除
✔ 一个实用的折中：类型擦除边界

内部逻辑用模板/concept 享受零开销与强检查；在最外面的一层（比如"注册一个显示后端"的接口）用一次 类型擦除（虚表 / 函数指针表）把不同实现统一起来。这样热路径是静态的、边界是可扩展的。 第①册的 ops 表没有过时——它正好适合那个"边界"。 擦除层别用 std::function 这类"可能走堆、且依赖异常运行时"的现成组件；在 MCU 上手写一个小函数指针表（或极简虚表）更可控、更省体积。

// display_erase.cpp —— 手写一张 vtbl，把不同实现统一到"边界"
#include <cstdint>

struct DisplayVtbl {                    // 手写的"虚表"，等价于第①册的 ops 表
    void     (*init)(void* self);
    void     (*clear)(void* self, uint8_t on);
    uint16_t (*width)(const void* self);
};

template <class D>
struct DisplayModel {                   // 把任意具体类型适配成上面那张表
    static void     init(void* self)              { static_cast<D*>(self)->init(); }
    static void     clear(void* self, uint8_t on) { static_cast<D*>(self)->clear(on); }
    static uint16_t width(const void* self)       { return static_cast<const D*>(self)->width(); }
    static constexpr DisplayVtbl vtbl{&init, &clear, &width};
};

class St7789 {
public:
    explicit St7789(uint16_t w) noexcept : w_(w) {}
    void     init() noexcept {}
    void     clear(uint8_t) noexcept {}
    uint16_t width() const noexcept { return w_; }
private:
    uint16_t w_;
};

// 边界：只认 vtbl + void*，不同实现可以放进同一个数组、在运行期遍历
void bring_up(const DisplayVtbl* vt, void* self) {
    vt->init(self);
    vt->clear(self, 1);
    (void)vt->width(self);
}

void use(St7789& lcd) { bring_up(&DisplayModel<St7789>::vtbl, &lcd); }
✔ 这一层把两种方案接了起来

DisplayModel<D> 用模板在编译期生成"某类型怎么调"的静态函数（零开销、可内联）， 而 DisplayVtbl 把它们收成一张运行期的函数指针表 —— 于是热路径仍是静态的，边界却可以运行期切换/遍历。 这正是 §10.3 说的"内部 concept、边界擦除"的落地写法；它和第①册的 ops 表是同一个东西，只是填表由模板自动完成、不再手写。

10.4 重构的纪律（比技术更重要）

  1. 先测后改：重构前把行为测住（第①册 Module 07 的 PC 单元测试），改完立刻回归。
  2. 小步前进：一次只换一个模块、一个接口；用 extern "C" 让新旧共存（Module 09）。
  3. 盯住体积：每次改动都用 size/nm --size-sort 对比，别让模板实例化悄悄膨胀（Module 04）。
  4. 别为重构而重构：C 写得好好的、又没人会误用的地方，不必强行 C++ 化。收益要能说清。
✔ 重构后要盯的三个数
  • sizeof(对象)：重构后应只剩自身状态（如 St7789 的 w_ = 2 字节），不含 ops/ctx 指针。
  • nm --size-sort：看有没有某个实例化特别大；模板每多一种类型就多一份代码。
  • 整镜像 size：确认没有把 libstdc++/异常运行时拖进来（对照 §1.3 那个 566 KB 的教训）。

  1. 简答：用 concept + 模板重构 ops 表，最大的收益与最大的代价各是什么？

    收益：零 vptr/零 ctx、静态可内联、参数类型在编译期被检查、报错可读。代价：丢失运行期多态——不能把不同实现放进同一个基类指针/数组在运行期切换。

  2. 判断：有了 concept，ops 虚表就完全没用了。

    不是。需要"运行期在一批同接口不同实现间切换/遍历"时，仍要虚表或类型擦除。常见做法是内部用模板、边界用一次类型擦除，兼顾零开销与可扩展。

  3. 填空：重构的第一步应该是 ______，而不是直接改代码。

    先把行为测住（写测试）。重构改的是结构、不改行为，所以必须有能立刻判断"行为没变"的回归测试（第①册 Module 07）。

  4. 简答：重构时为什么每次都要看 size/nm --size-sort？

    因为模板/concept 会为每种类型实例化一份代码（Module 04 的膨胀问题）。不看体积，可能"重构后更安全了、但固件超了"。用 nm --size-sort 能发现异常大的实例化。

  5. 判断：一个项目应该"全量改成 C++"。

    不建议。稳妥路径是自下而上、逐文件：先把纯逻辑模块改成 C++ 并用 extern "C" 接回 C 工程，跑通验证再继续。C 写得好、没人误用的地方不必强行 C++ 化。

  6. 决策：minidrv 里"同一块 LCD，运行期可能换成另一种控制器"，该用 concept 泛型还是虚表/类型擦除？

    用类型擦除/虚表（如 display_erase.cpp 的 DisplayVtbl）——因为需要运行期在多个实现间切换/遍历，而 concept 泛型在编译期就把类型定死了。只有"编译期就确定是哪种 LCD、且要极致开销"时，才纯用 concept。

术语与符号对照表

本页是 B02 的单一事实源：verify/glossary.json 与下表逐条比对， 两边漂移（少了/多了/写错）会在构建时直接失败。改术语/符号时，两处必须同步。

术语

术语含义
RAIIResource Acquisition Is Initialization：构造获取资源、析构释放；任何正常离开作用域都触发析构，替掉易漏的 init/deinit 配对。
Rule of 0/3/5不直接持有资源就不写（Rule of 0）；持有资源则析构+拷贝构造+拷贝赋值三者齐写或齐禁（Rule of 3）；再要移动就加移动构造/赋值（Rule of 5）。
移动语义转移所有权而非复制：源对象交出资源后进入 valid-but-unspecified 状态。对句柄/缓冲只搬指针与长度。
constexpr函数/变量"可以在编译期求值"（也可运行期）；被运行期引用时才实体化进 .rodata。
consteval必须在编译期求值，否则编译失败；适合强制"查找表绝不在运行时重算"。
constinit要求变量做常量初始化，从而根本不存在跨 TU 的动态初始化顺序问题（SIOF）；不等于不可修改。
零开销抽象抽象在运行期不产生额外指令/存储（如可内联的模板、无 vptr 的静态分派）；代价通常转移到代码体积。
实例化膨胀模板/泛型为每种实参组合生成一份代码；用 --gc-sections 删未引用的、用 extern template 控制生成点。
CRTP奇异递归模板模式：基类以派生类为模板参数，编译期静态分派、无 vptr 的"继承+覆写"。
虚表运行期多态的实现：每对象一个 vptr，调用经间接跳转；关异常/RTTI 可减小体积。
标准布局standard-layout：布局与 C 兼容的充分前提（无虚函数、无访问控制混排等）；offsetof 也仅对它有标准保证。
placement new在给定的已有存储上调用构造函数；它不是 RAII，析构要显式调用，且同一存储上需先析构旧对象再构造新对象。

符号 / 构件类别说明
vptr隐藏成员含虚函数对象里的虚表指针；32 位 Cortex-M 上每对象 +4 字节。
.ARM.exidx只读段表驱动异常模型的展开表；-fexceptions 时出现，size 计入 text。
ldrex/strexARM 指令Cortex-M3+ 的独占读/写，用于无锁读-改-写（如 atomic fetch_add）。
dmb ishARM 指令数据内存屏障；release 在写前、acquire 在读后各一条。
__libc_init_array函数（libc）启动期遍历 .init_array 调用 C++ 全局构造；-nostartfiles 时需在 Reset_Handler 显式调用。
