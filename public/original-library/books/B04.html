Module 01 · 定位与边界

定位与边界

Python 在嵌入式里有两个位置：上位机（PC 上的工具/分析/CI）与设备端（MicroPython 固件）。 混淆这两者，是新手最常见的方向性错误。这一节先把"什么该放哪"划清楚。

◷ 约 55 分钟◈ CPython / MicroPython / CircuitPython⚑ 先分清位置

1.1 三种 Python，别混为一谈

实现跑在哪特点 / 适用
CPythonPC / 服务器 / Linux 边缘设备标准库齐全、第三方库海量；本册的上位机主角（pyserial/numpy/pandas/matplotlib）
MicroPythonMCU（ESP32/STM32/RP2040）固件里带解释器，约 256KB Flash 起；machine 直接操作外设；支持 viper 加速
CircuitPythonMCU（Adafruit 生态）MicroPython 分支：USB 拖拽式部署、库友好；性能与底层控制略弱于原版

一句话：CPython 是"工具"，MicroPython 是"设备上的一层薄抽象"。前者决定你的开发效率，后者决定你能不能把 Python 直接跑在板子上。

1.2 分工边界：什么放设备端、什么放上位机

FIG 1.1 分工边界：硬实时与体积敏感留给设备，计算与流程留给上位机
判断口诀：与"时间/体积/功耗"强相关 → 设备端；与"效率/数据/流程"强相关 → 上位机。MicroPython 只在"设备端但要求不高"的缝隙里用。

1.3 同一件功能：MicroPython 与 CPython 写法对照

功能相同——"点亮 LED、按秒闪烁、打印状态"。左边是设备端 MicroPython（machine 直接操作硬件）， 右边是上位机 CPython（通过串口与设备交互）。注意 time.sleep_ms 与 time.sleep 这类"看着像、其实不同"的 API。

blink_mp.py — 设备端 MicroPython：直接操作硬件 Python 
# blink_mp.py —— 跑在 MCU 上的 MicroPython（ESP32/STM32）
from machine import Pin
import time

led = Pin(2, Pin.OUT)          # 设备端：直接拿到一个引脚对象

n = 0
while True:
    led.value(n % 2)           # 0/1 翻转
    time.sleep_ms(500)         # MicroPython 特有的毫秒延时
    print("tick", n)           # 经串口 REPL / UART 输出
    n += 1
monitor_pc.py — 上位机 CPython：通过串口观察设备 Python 
# monitor_pc.py —— 跑在 PC 上的 CPython（需要 pyserial）
import serial
import time

# 打开设备串口（端口名按你的系统改）
with serial.Serial("COM5", 115200, timeout=1) as ser:
    while True:
        line = ser.readline()          # 读到换行；空表示超时
        if line:
            print("设备:", line.decode(errors="replace").strip())
        time.sleep(0.1)
◆ 三个"看着一样、其实不同"的点
  • time.sleep_ms（设备端，整数毫秒）vs time.sleep（上位机，浮点秒）——写错就是"睡 0 秒"或"睡 500 秒"。
  • 设备端 print 走 REPL/UART 调试口，不是 PC 的终端；上位机要看，得用 pyserial 读。
  • 设备端内存以 KB 计：while True 里别不断创建对象（GC 停顿，见 M02）。

1.4 什么时候别用 MicroPython

需求结论
硬实时（μs 级中断响应、严格抖动）不用——解释器与 GC 会带来不可控抖动
极致 BOM（几 KB Flash / 极低功耗）不用——解释器本身就要几百 KB
寄存器级时序、DMA 精调不用——用 C/Rust；MicroPython 只暴露高层 API
快速原型、教学、胶水逻辑、现场脚本合适——改一行即生效，REPL 即时验证
⚠ 本册的立场

设备端主力仍是 C/C++/Rust（见第①②③册）；MicroPython 是"在某些场合更快的选择"，不是替代。 而上位机 Python 几乎总是值得——它把验证与迭代的成本降到很低。

Module 02 · 设备端深入

MicroPython 深入

把 Python 跑在 MCU 上，代价与边界都来自"解释器 + 堆"。这一节讲清 MicroPython 的内存与 GC、 machine 模块、定时中断，以及两个提速/扩展手段：viper 与 C 模块。

◷ 约 70 分钟◈ GC · machine · 定时中断 · viper⚑ 边界就在内存

2.1 运行时与内存：解释器 + 堆 + 固件

FIG 2.1 MicroPython 运行时：固件（Flash）与 GC 堆（RAM）各占一块
理解这张图就理解了一半边界：Flash 放"不会变的东西"（固件+可选 frozen 模块），RAM 靠 GC 管"运行时对象"。内存不足、GC 停顿都出在 RAM 那一块。

内存紧张时可主动回收：gc.collect()，并配合 gc.mem_free() 观察堆水位——这也是排查"跑着跑着 OOM"的第一步。

2.2 machine 模块：GPIO / UART / Timer

machine 是设备端 Python 与硬件之间的接口层：machine.Pin、machine.UART、machine.Timer，配合 time.sleep_ms 等。它比 C 的寄存器操作高一层，因此也用不到指针/位掩码——这正是它"上手快"的原因，也是"控制力有限"的原因。

machine_demo.py — GPIO / UART / Timer 的最小用法 Python 
# machine_demo.py —— 跑在 MCU 上（ESP32）
from machine import Pin, UART
import time

led = Pin(2, Pin.OUT)
uart = UART(1, baudrate=115200, tx=17, rx=16)

def heartbeat():
    led.value(not led.value())      # 翻转
    uart.write(b"HB\n")             # 发一行给上位机

while True:
    heartbeat()
    time.sleep_ms(1000)

2.3 定时中断：在中断里只做"最小的事"

用 machine.Timer 周期回调替代"主循环里 sleep 计数"——定时更准，也让主循环空出来干别的。 但要注意：MicroPython 的回调运行在中断上下文，和 C 的 ISR 纪律一样——不做重活、不长时间分配/打印。

timer_isr.py — 定时中断 + 主循环分工 Python 
# timer_isr.py —— 中断里只翻转标志，重活留给主循环
from machine import Pin, Timer
import time

led = Pin(2, Pin.OUT)
flag = False                     # 简单共享标志

def tick(t):
    global flag
    flag = True                  # 中断里：只做最短的操作

tim = Timer(0)
tim.init(period=500, mode=Timer.PERIODIC, callback=tick)   # 每 500ms

while True:
    if flag:
        flag = False
        led.value(not led.value())   # 重活放主循环
    time.sleep_ms(10)
⚠ 中断回调里的三条纪律（与 C 的 ISR 完全一致）
  • 不做重活：不要在里面做长循环、复杂计算；只置标志/入队。
  • 谨慎分配/打印：回调里创建对象或 print 可能触发 GC 或阻塞，拉长中断时间。
  • 共享变量要小心：MicroPython 下同样有"主循环与中断同时读写"的问题；能用"中断只写、主循环只读的单字标志"就用它。

2.4 提速：viper 与 native

纯 Python 的逐字节处理在 MCU 上很慢。@micropython.viper 让函数走定长整数的专门编译路径，接近机器码； @micropython.native 是中间的收益。代价是类型受限、不能用任意 Python 特性。

viper_crc.py — 用 viper 加速逐位 CRC8 Python 
# viper_crc.py —— 用 viper 把热点函数编成近机器码
import micropython

@micropython.viper
def crc8(data: ptr8, n: int) -> int:
    c = 0
    for i in range(n):
        c ^= data[i]
        for _ in range(8):
            c = ((c << 1) ^ 0x07) & 0xFF if (c & 0x80) else (c << 1) & 0xFF
    return c

buf = bytearray(b"hello")
print(crc8(buf, len(buf)))
◆ viper / native 的取舍
  • viper：最快，但类型是 int/ptr/ptr8/ptr16/ptr32 等定长，整数运算可能回绕；只在热点函数上用。
  • native：比普通 Python 快、比 viper 宽松；作为中间档。
  • 把它们局部用在数据密集循环（CRC/协议解析/滤波），而不是整段程序——否则可读性与兼容性双输。

2.5 与 C 扩展：什么时候必须下沉

3.1 最小串口收发

pyserial 的入口极小：Serial(port, baudrate, timeout)。关键是理解两个方法： readline()（读到换行，适合行式调试输出）与 read(n)（读固定字节，适合二进制帧）。 务必设 timeout，否则读不到数据会永久阻塞。

serial_io.py — 上位机收发（行式命令） Python 
# serial_io.py —— 打开串口、发命令、读回显
import serial, time

def open_port(port="COM5", baud=115200):
    return serial.Serial(port, baud, timeout=1)     # 关键：timeout 避免永久阻塞

def cmd(ser, text):
    ser.write((text + "\n").encode())
    ser.flush()
    time.sleep(0.1)
    return ser.readline().decode(errors="replace").strip()

if __name__ == "__main__":
    with open_port() as ser:
        print("版本:", cmd(ser, "version"))
        print("状态:", cmd(ser, "status"))
⚠ 上位机脚本最容易踩的三个坑
  • 不设 timeout：设备没回就卡死；至少设 1s，并据此判断"超时"。
  • 把"写"当"收到"：write 只表示进入发送缓冲，回包要另读。
  • 换行差异：设备可能发 \r\n，读回后统一 strip()。

3.2 帧结构与解析：半包与粘包

二进制协议必须自己定帧。绝不假设"一次 read = 一帧"——串口数据可能被拆成半包，也可能几帧粘在一起。 正确做法：维护一个缓冲，feed 新数据、循环尝试"拼出一整帧"；解析时可用 memoryview 在缓冲上零拷贝按偏移读取。

解析器的核心循环：找 SYNC → 读 LEN → 足长才取帧 → 校验 → 消费并继续。不足就等下一次 feed。下面的脚本本机实测跑过。
frame_codec.py — 组帧 + 流式解帧（可跑） Python 
# frame_codec.py —— 组帧 + 流式解帧（处理半包/粘包）
import struct

SYNC = b'\xAA\x55'

def encode(payload: bytes) -> bytes:
    n = len(payload)
    body = bytes([n]) + payload
    chk = 0
    for b in body:
        chk ^= b
    return SYNC + body + bytes([chk])

class FrameParser:
    """把字节流按帧切出来；不完整就留在缓冲里等下一次 feed。"""
    def __init__(self):
        self.buf = bytearray()

    def feed(self, data: bytes):
        self.buf += data
        out = []
        while True:
            i = self.buf.find(SYNC)
            if i < 0 or len(self.buf) < i + 3:
                break
            if i > 0:
                del self.buf[:i]
            n = self.buf[2]
            total = 2 + 1 + n + 1
            if len(self.buf) < total:
                break                       # 半包：等更多数据
            frame = bytes(self.buf[:total])
            chk = 0
            for b in frame[2:-1]:
                chk ^= b
            out.append((frame[3:-1], chk == frame[-1]))
            del self.buf[:total]
        return out

if __name__ == "__main__":
    f1 = encode(b"HELLO")
    f2 = encode(b"OK")
    print("frame1 hex =", f1.hex())
    p = FrameParser()
    print("feed half(3B) ->", p.feed(f1[:3]))
    print("feed rest     ->", p.feed(f1[3:]))
    print("feed two(glue)->", p.feed(f2 + f2))

3.3 超时与重传：把"设备没回"变成可测的事

reqresp.py — 请求-应答 + 超时重传 Python 
# reqresp.py —— 发一帧、等应答；超时则重传（最多 N 次）
import struct, time

def build(seq: int, payload: bytes) -> bytes:
    body = struct.pack("<BH", seq, len(payload)) + payload
    chk = 0
    for b in body:
        chk ^= b
    return b'\xAA\x55' + body + bytes([chk])

def transact(send, recv, seq, payload, tries=3, timeout=0.5):
    for k in range(tries):
        send(build(seq, payload))
        deadline = time.monotonic() + timeout
        while time.monotonic() < deadline:
            frame = recv()                 # 返回 bytes 或 None
            if frame:
                return frame
        # 超时：下一轮重传（seq 不变，便于设备去重）
    raise TimeoutError(f"no reply for seq={seq} after {tries} tries")
◆ 为什么用 seq 而不是"直接重发"

重传可能造成设备收到两份同一请求。带上 seq，设备端可对重复序号去重（只处理一次、但都回复）， 这样"请求-应答"在网络/串口不可靠时才是幂等的。这与第②册协议编排里"序号与去重"是同一件事。

def outliers(xs, k=2):
    mu = sum(xs) / len(xs)
    sd = (sum((x - mu) ** 2 for x in xs) / len(xs)) ** 0.5
    return [x for x in xs if sd and abs(x - mu) > k * sd]

◆ 四条纪律
  • 传列表、不要拼字符串：run(["esptool","--port",p,"write_flash",...])；拼 shell 字符串会遇到空格/注入问题。

import subprocess, sys, argparse

def run(cmd, dry=False):
    print("$", " ".join(cmd))
    if dry:
        return 0
    return subprocess.run(cmd, check=True).returncode      # check=True：失败即抛异常

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--dry-run", action="store_true")
    ap.add_argument("--port", default="COM5")
    a = ap.parse_args()

    run([sys.executable, "-m", "py_compile", "protocol.py"], dry=a.dry_run)          # 1) 语法门禁

    run([sys.executable, "make_report.py"], dry=a.dry_run)                            # 4) 出报告
    print("pipeline done.")

if __name__ == "__main__":
    main()

# plotter.py —— 最小实时曲线：串口线程 + tkinter 主线程
import threading, queue, serial, tkinter as tk

q = queue.Queue(maxsize=1000)          # 线程间用队列传数据（有界，防积压）

def reader(ser, stop):
    while not stop.is_set():
        line = ser.readline()          # 阻塞读（受 timeout 控制）
        if line:
            try:
                q.put_nowait(float(line))
            except (ValueError, queue.Full):
                pass                   # 丢非数字/满了就丢，绝不在采集线程里阻塞

class App:
    def __init__(self, root, ser):
        self.root, self.ser = root, ser
        self.data = []
        self.cv = tk.Canvas(root, width=600, height=200, bg="#0B1110")
        self.cv.pack()
        self.stop = threading.Event()
        threading.Thread(target=reader, args=(ser, self.stop), daemon=True).start()
        self._tick()
    def _tick(self):
        while not q.empty():           # 只取走队列里的最新数据
            self.data.append(q.get())
            del self.data[:-300]       # 只留最近 300 点
        self._draw()
        self.root.after(50, self._tick)  # 50ms 刷新
    def _draw(self):
        self.cv.delete("all")
        n = len(self.data)
        if n > 1:
            pts = [(20 + i*560/(n-1), 180 - (v % 4096)/4096*160) for i, v in enumerate(self.data)]
            self.cv.create_line(*[c for p in pts for c in p], fill="#4EF08A", width=1.4)

if __name__ == "__main__":
    ser = serial.Serial("COM5", 115200, timeout=1)
    root = tk.Tk(); root.title("serial plotter")
    App(root, ser); root.mainloop()
◆ 为什么"串口线程 + 队列 + after 刷新"是标准结构
  • UI 线程绝不阻塞：readline() 在后台线程做，慢的是它、不是界面。
  • 队列有界：采集快、UI 慢时丢旧数据，而不是无限积压把内存吃光。
  • 刷屏只画最近 N 点：曲线是"窗口"，不是"历史全量"。

# ota_ui.py —— 把固件分块下发，并按进度刷新界面
def send_firmware(ser, blob: bytes, chunk=1024, on_progress=lambda p: None):
    total = len(blob)
    for off in range(0, total, chunk):
        part = blob[off:off + chunk]
        ser.write(b"%06X" % off + part)     # 偏移 + 数据（示意协议）
        ack = ser.read(1)
        if ack != b"K":
            raise IOError(f"chunk at {off} not acked")
        on_progress((off + len(part)) / total)   # 回调 → UI 进度条
    ser.write(b"DONE")

# collect_imu.py —— 采集一段带标签的 IMU 数据
import serial, csv, time

def collect(session_id: int, label: str, seconds: float = 5.0, port="COM5"):
    path = f"raw/sess{session_id:02d}_{label}.csv"
    t0 = time.monotonic()
    with serial.Serial(port, 115200, timeout=1) as ser, open(path, "w", newline="") as f:
        w = csv.writer(f); w.writerow(["t", "ax", "ay", "az"])
        while time.monotonic() - t0 < seconds:
            line = ser.readline().decode(errors="replace").strip()   # 设备发 "ax,ay,az"
            if not line:
                continue
            try:
                ax, ay, az = (float(v) for v in line.split(","))
            except ValueError:
                continue                                             # 跳过非数据行
            w.writerow([f"{time.monotonic()-t0:.3f}", ax, ay, az])
    print("saved", path)

if __name__ == "__main__":
    collect(session_id=0, label="idle")
◆ 采集阶段的三个"必须"
  • 必须带时间戳：后面做重采样、对齐、去抖都靠它。
  • 必须带标签与会话号：标签是监督信号；会话号用于后面"按会话切分"。
  • 必须记录元数据：采样率、量程、设备/固件版本、采集人——复现的命根子。

7.3 组织与切分：为什么"按会话"而不是"按样本"

数据集目录建议固定为 raw/（原始，不改）、train/、val/、metadata.json。 切分最关键的纪律：同一段会话的样本不能同时进训练和验证——否则模型"见过"验证集，指标虚高（数据泄漏）。

split_dataset.py — 按会话切分（可跑） Python 
# split_dataset.py —— 生成会话数据，按"会话"切分训练/验证（避免数据泄漏）
import os, random
from collections import Counter

random.seed(7)
SESSIONS, PER_SESSION = 6, 20
labels = ["idle", "shake", "tilt"]

def make_dataset(root="dataset"):
    os.makedirs(os.path.join(root, "raw"), exist_ok=True)
    meta = []
    for s in range(SESSIONS):
        label = labels[s % len(labels)]
        for i in range(PER_SESSION):
            name = f"sess{s:02d}_{label}_{i:03d}.csv"
            open(os.path.join(root, "raw", name), "w").write("ax,ay,az\n0,0,1\n")
            meta.append({"file": name, "session": s, "label": label})
    return meta

def split(meta, val_ratio=0.34):
    sess = sorted({m["session"] for m in meta})
    n_val = max(1, round(len(sess) * val_ratio))
    val_sess = set(sess[-n_val:])                 # 按会话划分，而非按样本
    train = [m for m in meta if m["session"] not in val_sess]
    val   = [m for m in meta if m["session"] in val_sess]
    return train, val, sorted(val_sess)

if __name__ == "__main__":
    meta = make_dataset()
    train, val, vs = split(meta)
    print(f"sessions={len({m['session'] for m in meta})}  samples={len(meta)}")
    print(f"train={len(train)}  val={len(val)}  val_sessions={vs}")
    print("train labels:", dict(Counter(m["label"] for m in train)))
    print("val   labels:", dict(Counter(m["label"] for m in val)))

  1. 简答：为什么训练/验证要"按会话"而不是"按样本"随机切？

    同一会话的样本高度相关（同一次佩戴/同一环境），若随机切会把"近邻"分到两边，验证集等于"见过"，指标虚高——即数据泄漏。

    还要看类别覆盖。本例验证集缺 idle，即使无泄漏，也无法评估该类——覆盖不全是切分的第二个检查点。

  3. 诊断：采集脚本把非数据行（如设备日志）也写进了 CSV，会造成什么？

    后面解析会报错或污染统计；应在采集时就过滤（try/except ValueError: continue），或严格用帧解析（M03）区分数据与日志。

    不应。原始数据应只读、先备份；清洗/切分产物写到别的目录。否则无法复现，也无法回溯标注错误。

机制与契约

数据契约至少包含版本、会话、时刻、序号、单位、原始值、质量与参数版本。保留原始输入，再保存处理结果；修订参数后可以用同一输入解释差异。定点对拍必须约定缩放、饱和和舍入：Python // 对负数向下取整，而 C11 整数除法向零截断，本例先取绝对值再恢复符号来匹配 C。比较整数算法应精确一致，浮点算法用声明的绝对/相对容差。

边界与误用
