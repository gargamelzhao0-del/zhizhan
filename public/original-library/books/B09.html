Module 01 · 系统与启动

SoC 架构与启动链.

嵌入式 Linux 的启动是一条逐跳接力：ROM Code → SPL → U-Boot → Kernel → init，每一跳只做一小步，把下一跳加载起来。定位启动问题的唯一可靠方法，是串口抓全程日志、先确定卡在哪一跳。

前置：了解 MCU 上电复位流程、串口 console，以及 SoC 有片内 ROM 与外部启动介质。◷ 约 44 分钟◈ STM32MP1 / i.MX6ULL / V3s 三路线对照⚑ 主机模型；目标构建与测量按章验收能力目标：能把启动日志分成 ROM→SPL→U-Boot→Kernel→init 五跳，量化各跳耗时并定位卡在哪一跳。
本章速览
  • 启动链是 ROM→SPL→U-Boot→Kernel→init 逐跳接力，每跳只做一小步。
  • 串口 console 抓全程日志：先确定“卡在哪一跳”，再查那一跳。
  • 每跳的启动介质、加载地址与 bootargs 必须一致；不一致就停在上一跳。

1.1 五跳接力：每一跳只负责“把下一跳拉起来”

嵌入式 Linux 的启动不像 PC 一键到底，而是分级接力：片内 ROM 只会最少的事，它把 SPL 拉起来；SPL 初始化 DDR 后把 U-Boot 拉起来；U-Boot 加载内核与设备树并传参；内核 probe 驱动、挂根、启动用户态 init。每一跳的能力都在放大，问题也逐跳变具体。

为什么“分层”是嵌入式 Linux 的设计基石

ROM 不可改，所以只做最小的事；把复杂逻辑（DDR、加载、启动参数）交给可升级的 SPL/U-Boot。这带来两个好处：可升级（改 SPL/U-Boot 即可换启动策略）与可诊断（每跳能打印，逐跳定位）。

1.5 常见误区与排障

失败路径与排障
  • 只改设备树不重编 dtb：U-Boot 加载的是旧 dtb，改动不生效。
  • bootargs 里 console/root 写错：内核起了却看不到 log 或找不到根。
  • 内核与 dtb 不匹配：驱动 probe 失败，设备“凭空消失”。
  • 不接串口：什么日志都没有，只能猜。
◆ 自测 · Module 01（先答再看）

  1. 上电后串口完全没有输出，最可能卡在哪一跳？

    查看答案

    最可能卡在 ROM/SPL：DDR 未初始化，或介质里没有有效的 SPL。若已打印 SPL 但之后无输出，则查 SPL→U-Boot 的加载地址与介质。

  2. 启动日志里 U-Boot 到 Kernel 花了 582ms、Kernel 到 init 花了 2100ms，先优化哪一跳？

    查看答案

    先优化耗时最大的 Kernel→init（2100ms）：查内核驱动 probe、延迟初始化、根文件系统挂载。“哪一跳最大先动哪一跳”是启动优化的基本纪律。

设备树.

设备树把“硬件长什么样”从内核代码里拿出来，用节点与属性描述。驱动靠 compatible 匹配设备，status 决定是否使能。读懂它，才能让“设备树写了但驱动不 probe”不再是玄学。

3.1 设备树解决什么问题：硬件的“数据化描述”

如果把每块板的硬件差异都写进内核源码，内核会被板级细节淹没。设备树把硬件描述外置成数据：同一份内核，配不同 dtb 就能跑不同板子。驱动只认 compatible 字符串，不关心具体是哪块板。

6.1 介质 → 文件系统 → 升级落点

  3. ③ 设备树（M03）——按路径与 compatible 匹配；验收：目标设备 status=okay 且驱动 probe。
  4. ④ 内核（M04）——defconfig + 片段裁剪；验收：bootargs 正确、启动时间可量化。
  5. ⑤ 根文件系统（M05）——busybox/init/库齐备；验收：布局自检 0 错误、能到 init。
  6. ⑥ 存储（M06）——分区与文件系统选型；验收：root= 与分区一致、坏块有处理。
  7. ⑦ 调试（M07）——dmesg/ftrace/strace/pstore；验收：能定位“卡在哪、慢在哪、崩在哪”。
  8. ⑧ 系统使用（M08）——权限/进程/挂载/设备节点/网络/服务；验收：非 root 跑应用、服务可托管。
  9. ⑨ 交付（M09）——BSP 版本化 + SDK；验收：换机器能复现出同一镜像。
  10. ⑩ 恢复（M10）——labs/capstone_image.sh；验收：A/B 升级失败能自动回滚，recovery 能救砖。

术语表.

按“先定义、再结论”的方式收口；不同路线/厂商的叫法差异也标注在此。

BSP
板级支持包：Bootloader + 内核 + 设备树 + 根文件系统 + 驱动的一组版本化产物。
ROM Code
SoC 固化的一级引导，只做最少的初始化并按启动介质加载 SPL/FSBL。
SPL / FSBL
二级引导，初始化 DDR 时钟等，再把 U-Boot 加载起来。
U-Boot
通用引导器：加载内核与设备树、传 bootargs、提供升级/回滚环境变量。
设备树 (DTS/DTB)
描述硬件的节点与属性；内核据此匹配驱动，与代码解耦。
compatible
设备与驱动的匹配字符串；不匹配则驱动不 probe。
overlay
设备树覆盖层，用于板级差异，避免改 SoC 公共 dtsi。
sysroot
交叉工具链对应的目标根库；内核/应用必须用同一套。
Buildroot
轻量构建系统：一个配置产出内核+rootfs+镜像，直接快速。
Yocto
元数据/层构建系统：可裁剪、可复现、标准化，学习曲线陡。
initramfs
内存中的早期根文件系统（cpio 归档），常用于引导与恢复。
busybox
把大量 UNIX 工具塞进一个可执行文件；最小 rootfs 的基石。
overlayfs
联合文件系统：只读根 + 可写层，系统可恢复、升级更简单。
UBIFS / F2FS
NAND 用 UBIFS（含坏块/磨损处理）；闪存友好型还有 F2FS。
A/B 分区
两套系统分区交替升级，配合 bootcount 实现失败自动回退。
bootcount / bootslot
U-Boot 环境变量：记录启动尝试次数与当前槽位，决定是否回滚。
recovery 分区
独立的最小系统，用于恢复损坏的 rootfs 或重刷固件。
pstore / ramoops
把内核崩溃日志保留在内存/闪存，重启后仍可读取。
swupdate / RAUC
嵌入式 OTA 框架：签名校验、A/B 更新、回滚。
